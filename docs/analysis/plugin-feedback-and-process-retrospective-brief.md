# 需求插件：上下文反馈与自动过程复盘——研究判断和开发指令

日期：2026-11-02。性质：设计与开发执行规格；本次未实施功能，未进行性能实测。

## 1. 对用户意图的判断

意图合理，建议落地为两个互补入口：随时可用的“反馈与建议”，以及可开关的“自动过程复盘”。二者共同产出有证据、可确认、可进入现有交付流程的插件改进需求。

不建议把设置直接命名为“自动优化”。这个名字容易让人以为打开后会自行修改代码，而用户这次明确要求的是观察、分析、提出建议并转需求。首版应自动形成待确认需求，不自动开发、改提示词、调整权限或发布插件；后续仍由现有确认与开发授权流程推进。

应批判性处理五个前提：

1. **操作多不一定设计差。** 用户思考、复杂业务讨论、正常否决与主动编辑都有价值。不能仅凭停留时间、点击数或撤销次数推断缺陷，更不能评价用户能力。
2. **开发成功不代表流程好，开发失败也不代表插件有错。** 模型供应商、项目代码、需求变化和插件流程应分开归因；允许证据不足、不提建议。
3. **记录全部内容不等于保留有效上下文。** 需要结构化事件、版本、决定、产物和少量相关片段，避免全量聊天和截图堆积加重性能及分析成本。
4. **“完成开发”不是单一事件。** AI 空闲、执行 run 结束、测试通过、生成候选和用户验收是不同里程碑；不能看到代理停止输出就认定需求完成。
5. **生成更多需求不是优化成果。** 要考察建议是否有证据、是否被采纳、改动后同类任务是否改善，以及是否引入质量回退。允许一次完整复盘发现零条建议。

## 2. 可交给 Harness 执行的开发指令

请在真实需求插件中实现下述能力，先核验当前代码与接口，再按切片开发。保护工作区既有未提交修改，复用现有存储、需求澄清、失败监控和开发流程。不要只交静态原型或概念方案。

### A. 产品定义与流程

提供两个入口：

- **反馈与建议：** 用户随时发现问题时，快速表达，并保存当时上下文；可保存反馈，也可生成待确认需求。
- **自动过程复盘：** 用户开启后，记录需求插件内的关键过程事件，在真实交付里程碑后后台分析；针对有证据的插件改进自动生成待确认需求。

共用链路：

`上下文/事件 → 观察事实 → 原因假设与归因 → 去重 → 改进需求（待确认） → 用户确认 → 现有开发授权 → 实施与验证 → 效果回看`

自动记录、自动分析、自动生成需求分别有清晰状态，不等同于自动批准或自动开发。整个建议分析过程不阻塞用户当前需求推进。

### B. 手动反馈入口

1. 在插件全局工具栏提供固定“反馈与建议”入口；在澄清、评审、运行、测试和验收页面提供上下文相关入口。若当前是模态界面，也必须能打开反馈而不丢失原表单，不叠加多层难以操作的模态。
2. 点击时立即冻结当前上下文版本。不能等用户写完建议时再抓取已变化的页面。
3. 使用紧凑侧栏或非破坏性反馈面板。只要求填写“哪里不顺，或希望怎样改变”；类别默认“待判断”，可选缺陷、体验优化、新能力。不能让用户先完成长需求表。
4. 展示可编辑的上下文摘要：所在页面/阶段、当前需求、最近相关事件、截图或文本摘录、目标产品、需求接收工作区。用户可去掉不相关材料。
5. 原输入、未提交回答、焦点和滚动位置保持；关闭反馈返回原处。截图为主动附加能力，不默认持续录屏。没有历史记录时明确显示“仅保存当前状态”，不假装保存了完整操作过程。
6. 操作提供“保存反馈”和“生成需求”。生成需求先可靠保存反馈与上下文，再异步生成需求草稿，状态可见。未完成原因分析不能使反馈丢失。
7. 用户表达已清楚时直接生成待确认需求；仅在会改变范围或验收的关键歧义上，调用已有澄清流程。不要把提建议变成另一次十分钟访谈。
8. 回执给出反馈 ID、保存状态及关联需求入口。失败重试或双击不重复创建；用户保留补充与更正历史。

### C. 必须保留的上下文

建立版本化 ContextEnvelope，字段按可用性记录，不允许编造缺失字段：

```text
feedbackId / contextSnapshotId / capturedAt / schemaVersion
observedWorkspace: 稳定 ID、项目 ID、允许显示的路径
targetProduct: harness-requirements-plugin、组件与插件版本
destinationWorkspace: 插件改进需求接收工作区（可空）
ui: 页面、阶段、可序列化视图状态、未提交内容摘要
links: intentSessionId / requirementId / requirementRevision
       runIds / candidateId / acceptanceDecisionId / existingFailureIds
runtime: 宿主/插件/模型配置标识、实际相关的异常及耗时
evidence: 事件范围、可选文本片段、附件引用与内容 hash
userStatement: 用户原话与期望
captureBoundary: 已覆盖/未覆盖阶段、截断、缺失材料
```

需求 ID 不是全局唯一关联键，应连同工作区与稳定内部标识保存；若允许重复业务 ID，不能只依赖其定位。

上下文以有界数据和不可变快照保存，既保留引用又保留复核所需的最小事实。临时日志被清理后，关键证据不能全部失效。

不记录密码、密钥、认证头和不相关文件。内容在进入分析请求前脱敏；使用现有模型通道，在设置中如实说明会发送哪些材料。附件中的指令按证据数据处理，不成为执行授权。

### D. 把发生位置与改进目标分开

这是核心正确性要求。

用户可能在业务项目 A 中使用插件，却在反馈插件自身的问题。必须分别保存：

- **发生位置：** 项目 A 的哪条需求、哪个阶段。
- **改进对象：** 需求插件或其确定组件。
- **需求归属：** 管理插件开发的工作区 B。

不能默认把所有反馈写入当前业务项目，也不能默认当前代码仓库就是插件开发仓库。

提供一次性设置“插件改进需求接收工作区”，使用宿主允许的工作区选择机制，校验目标项目身份及写入能力。已配置后自动提案不反复询问。

未配置、无权限或目标不可达时，先在持久反馈/改进收件箱保存待路由项，明确“尚未转为需求”；允许后续配置后幂等投递。不能静默退回业务项目或显示转化成功。

跨工作区投递只携带必要的脱敏证据摘要；业务项目原始材料留在来源工作区，权限不足时明确标注不可访问，不伪造链接可用。目标根路径从可信工作区映射解析，不能让模型输出任意文件路径。

### E. 自动过程复盘设置

首版默认关闭，用户主动开启。手动反馈始终可用，已有失败监控开关保持独立。

设置至少包含：

- 自动过程复盘启用/关闭。
- 作用工作区及覆盖阶段。
- 插件改进需求接收工作区。
- 上下文内容范围、附件是否纳入及保留期限。
- 分析预算与通知偏好。

开启表示允许在设定范围记录必要事件并使用现有模型进行复盘、自动生成待确认需求，不表示允许自动修复或发布。

关闭后停止新的专用采集与新复盘调度。尚未开始任务取消；正在执行任务尽力取消，关闭后通过当前设置版本再次校验，禁止迟到结果自动转需求。原业务运行日志与历史反馈保留并可查看；已经发到模型的请求无法当作未发送，应如实呈现状态。

已保存复盘可由用户主动重新分析。不能关掉失败监控，或删除业务执行所必需的日志，来实现本开关。

### F. 观察什么，不观察什么

记录关键语义事件，不把全屏录制或鼠标轨迹当基础设施。优先接入真实业务服务和后端生命周期，前端补充必要体验事件。

事件包括：

- 意图提交、澄清问题产生、回答保存、重复问题、决定修改与冲突。
- 评审开始/结束、意见采纳/拒绝、阻塞原因及后续处置。
- 开发启动/恢复/暂停、真实工具失败、重试、依赖和交接问题。
- 测试及验收结果、回归、人工修正、用户确认与需求变更。
- 用户主动反馈、等待阶段与实际耗时。

事件具有稳定 ID、工作区/会话/需求/运行关联、阶段、时间、来源、修订、因果关联或可靠序号。区分模型等待、服务处理、用户思考和主动暂停；跨进程时长不能盲目相减不同主机时钟。

用户实际打了多少字、点击了多少次不能直接判定体验差。关注可复核结果，例如同一已确认决定被重复追问、合法回答被覆盖、需求已明确却反复询问相同产品行为。

从开启后开始记录。中途开启的需求标记部分覆盖；可读取现有持久产物补充，但不得宣称已经观察未记录阶段。

### G. 定义复盘触发，禁止“AI 空闲即完成”

建立项目内需求交付周期标识 deliveryCycleId：绑定需求基线修订、纳入的 run/候选及决定。同一需求可能有多轮交付；同一轮可能有多个 run。

对以下里程碑分别处理：

1. **开发交付形成候选且进入待验收：** 自动形成“开发阶段复盘”，覆盖至本次候选，标记最终效果尚未验证。
2. **用户对候选完成验收：** 形成或更新该周期的“完整过程复盘”，加入测试、验收与返工事实。自动调度不要求用户额外点一次复盘。
3. **失败、暂停、取消或等待输入：** 保存事件；复用既有失败监控。可提供手动“复盘到当前阶段”，不能标为成功完成。

若验收不通过后再次开发，沿用或开启新周期需有明确规则，绑定新的候选/基线并保留关系。仅修改标签或无关元数据不应重跑全量复盘。

复盘任务的幂等键包含工作区、需求内部 ID、周期、里程碑、证据快照与分析策略版本。页面刷新、重复事件、重启不会重复提单；新验收证据更新原复盘并合并相关建议。

不依赖临时前端回调实现唯一触发。使用持久任务及启动后的有界补偿扫描/对账，队列恢复时重新校验设置和证据版本。

### H. 分析与归因规则

复盘至少关注六个问题：

- 用户目标在需求、实现与验收之间是否发生未经确认的漂移。
- 澄清是否遗漏关键决定或重复询问已明确内容。
- 开发是否因需求不完整反复反问，原因是什么。
- 评审、测试和验收是否发现了前面本可识别的问题。
- 插件是否增加了可避免的等待、手工搬运或信息丢失。
- 成功路径中有哪些值得保留的有效机制。

每个结论区分：

`观察事实 → 有证据支持的解释 → 其他可能原因 → 建议干预 → 如何验证`

归因至少支持：插件缺陷、插件体验/流程改进、需求自身问题、项目实现缺陷、模型/外部依赖问题、正常业务取舍、证据不足。

外部模型慢，不直接证明插件有缺陷；若插件每答一题都全量重生成且阻塞已有下一题，可以提出插件流程优化，但不能承诺消除供应商所有延迟。

测试红转绿不证明澄清过程好；用户否决建议不证明用户需求不合理；两次操作相邻不证明因果。单个观察可以生成明确标记待验证的候选，不能声称所有用户都受影响。

只有具备具体问题/机会、可定位证据、合理目标归属、可描述改动方向和可验证效果的建议，才自动转为待确认需求。证据不足保留观察或调查项，不能制造事实；无有效建议则保存“未发现足够证据支持新增改进需求”。

默认每个交付周期最多新增 3 条自动改进需求，其余排序保存为观察，不隐藏重要事实；手动反馈不受此上限限制。优先展示影响与证据，不编造 ROI、收益百分比或精确置信概率。

### I. 统一反馈与改进台账，复用既有失败台账

需要反馈记录与改进提案的版本化台账，但不要强行把所有优化伪装成失败。

最小逻辑实体：

- Feedback：用户原话、上下文快照、类别及转化状态。
- ProcessEvent：有界的生命周期事件。
- Retrospective：范围、证据快照、分析版本、覆盖率、任务结果与结论。
- ImprovementProposal：问题、归因、建议、证据、验证方法、目标、状态和关联需求。

这些是逻辑契约，按现有 `.alm/` 文件结构和持久任务能力落地，不要求新建数据库。

提案最小字段：

```text
id / revision / origin(manual-feedback|process-retrospective|failure-monitor)
kind(defect|improvement|capability|investigation)
targetProduct / targetComponent / destinationWorkspace
observedWorkspaces / relatedRequirementAndRunRefs / retrospectiveRefs
observations[] / evidenceRefs[] / hypotheses[] / alternativeCauses[]
problem / desiredOutcome / scope / exclusions / suggestedChange
acceptanceScenarios[] / effectCheck / missingInformation[]
fingerprint / linkedProposalOrDefect / requirementRef
status / creationReceipt / dispositionReason / updatedAt
```

来源、性质与改进对象是不同维度：来源=过程复盘不等于性质=缺陷。确认真实缺陷时可复用现有 `SOURCE: defect` 与缺陷台账；体验建议按兼容方案扩展来源/元数据，不能为了列表筛选一律打成缺陷。

手动反馈已记录但分析失败，应停留明确可重试状态；生成需求前后用持久回执/对账保证最终一致。不能先把提案标记已转需求，再静默忽略目标写入失败。

### J. 自动转需求、去重与授权

对满足条件的自动建议，在已配置目标工作区创建真实“待确认”需求，并在改进收件箱显示。不是只在报告里写“建议以后优化”。

确认需求与开始开发保持现有边界；可提供明确的“确认并开始开发”操作，但复盘开关本身不授权执行。

创建的需求至少包含问题/目标、复现或观察条件、预期/实际、影响范围、已知事实与假设、建议范围、验收场景和效果检查。不编造重现步骤、源代码位置、根因或重要性等级。

高影响未知保留，允许待确认记录存在但不能显示可直接开发；负责人和优先级沿用既有真实规则，建议值需标记为建议。

去重按“目标产品/组件 + 问题机制 + 期望行为 + 语义范围”判断，结合结构指纹与保守语义比较。需求 ID/run ID 属于发生实例，不能单独作为同一插件问题的指纹，否则跨需求永远无法合并。

手动反馈、失败监控、自动复盘发现同一问题时互相关联或合并证据，不创建三条需求。权限边界内共享摘要，不能跨项目读取未授权材料来去重。

同一问题新证据只追加观察，不覆盖用户已确认的范围。已忽略/暂缓的相同建议不反复催办；重大新证据或已关闭后再次出现可标疑似回归，仍待确认。

### K. 防止自我优化循环

改进提案保存 lineage：来源复盘、来源需求、改进目标和祖先提案。改进需求的开发也可以收集事件，但不能仅因“又运行了一次复盘”自动生成下一代改进需求。

复盘自己的调用失败复用失败日志，不同步递归调用复盘；设定同一 lineage 的自动提案上限和冷却策略。独立新问题可以保留观察并待确认，不被永久忽略。

模型建议本身不能作为已经发生缺陷的证据。不得通过反复读取自己上一轮的建议，把假设包装成多次独立观察。

### L. 交互、性能与设置行为

插件工具栏或设置提供“自动过程复盘：已关闭/观察中”；改进收件箱展示待确认数量。手动反馈独立可见。

需求交付里程碑后仅通知一次，如“本次过程复盘完成，发现 2 项改进建议”；无需建议时不弹干扰通知。报告入口与相关需求时间线可查。

复盘详情展示范围/覆盖阶段、关键时间线、事实与假设、建议、已有需求关系及本轮变化。可操作：查看或编辑需求、确认、暂缓、忽略、关联已有需求、标记误判、重新分析。

记录事件不等待模型。目标：普通交互额外开销 p95 ≤10ms；反馈面板本地反馈 ≤100ms；正常本地持久化回执 p95 ≤1s。以上需实测，未达到要报告。

事件批量落盘且有界，关键事件可按可靠性要求持久化；不为每次滚动或每条模型 token 同步写文件。明确单周期事件/内容上限、截断与保留期限，不能无限增长。

后台复盘低优先级、有限并发，前台模型任务优先；确认供应商与宿主是否支持抢占，否则避免同时占满配额并允许暂停后台任务。

首版建议单次分析最多一次格式修复、每周期有调用/token预算。超额、模型不可用或超时保留任务/证据并给状态，不无限重试。用户等待复盘时显示真实阶段和已用时，不编造完成百分比。

### M. 改进效果回看

把“建议已创建”“用户已确认”“改动已验收”和“效果已改善”分开。

每条改进需求附验证设计。例如“提交回答后仍需等待下一题”：比较同类任务的下一题可操作时间、模型调用数、重复追问率及需求语义质量。

区分修复前后插件版本、模型配置、任务类型与样本量。不同复杂度任务不能直接平均比较，也不能把同期换模型的收益全归给插件改动。

样本不足时标为效果待观察，必要时用固定配对场景验证。效果回退优先关联原改进，提出人工处理建议，不自动回滚用户代码或重新发布。

### N. 实施切片

1. **可用的手动闭环：** 固定入口、当前上下文快照、可靠保存、目标工作区、生成真实待确认需求和回执。
2. **有限过程记录：** 开关、事件关联、覆盖边界、关键等待指标、交付周期和持久触发；先提供可核对时间线。
3. **自动复盘与提案：** 分阶段报告、归因、预算、与现有失败监控去重、自动生成待确认需求。
4. **效果回看与健壮性：** 关闭语义、并发/恢复/跨工作区对账、误判反馈、版本对比与反循环。

不要为等待全量自动观测而拖延手动反馈入口。每个切片都在真实插件可用，新增接口名称以实际技术栈为准，不假设宿主已经提供所需事件 API。

### O. 验收清单

必须包含真实场景与有意义的自动测试：

1. 澄清表单未提交时打开反馈，保存点击时上下文；返回后输入与位置不丢。
2. 关闭自动复盘仍能反馈；未开启时不额外收集专用过程事件。
3. 中途开启只能声明部分覆盖。
4. 用户在业务项目反馈插件问题，正确路由插件开发工作区；未配置则明确待路由。
5. 目标无权限/不可达/写入失败保留反馈，重试和重启后不重复转需求。
6. 代理空闲/等待输入不被当作完成；取消关闭不被当作成功验收。
7. 候选待验收触发开发阶段复盘，验收后更新完整复盘，重复事件不重复提单。
8. 模型慢、正常业务否决、用户思考不会被直接判为插件缺陷。
9. 同一已答决定被重复追问有证据时，能提出针对性改进。
10. 成功过程无足够问题证据时，允许零建议。
11. 手动反馈、失败监控、自动复盘同一问题只有一个有效需求，保留来源证据。
12. 自动生成待确认需求后，不产生开发 run、不修改代码、不发布。
13. 关闭时的迟到分析不再自动转需求；已存在记录可查询。
14. 模型不可用、格式修复失败、服务重启、乱序事件可恢复且有状态。
15. 秘密字段被脱敏；不同工作区同需求 ID 不串线；证据指令不改变授权。
16. 复盘自身失败与改进需求不会引发无限提案循环。
17. 用户拒绝建议或修改范围后，后续追加证据不静默推翻决定。
18. 用户能从已生成需求追溯观察、证据、源周期、归因与缺失信息。
19. 后台分析不明显拖慢前台交互；用真实模型实测等待和调用预算。
20. 效果回看不把需求数量或测试通过直接等同于用户体验改善。

语义验收至少准备“真实插件缺陷、体验优化、业务缺陷、外部故障、正常过程、证据不足”六类，人工检查归因与建议质量。模型自评不能是唯一验收。

最终交付：现状差距、数据/事件与触发契约、修改文件、迁移说明、真实插件界面证据、手动反馈到需求及自动复盘到需求的端到端结果、开关和故障恢复验证、实际性能、未支持能力和仍需产品决定的事项。不能把历史测试记录当作本次验证。
