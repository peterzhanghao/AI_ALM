# DSH Desktop 多智能体优化需求插件：可行性与收益判定

日期：2026-11-04。范围：当前已安装 DSH Desktop 与 `D:/DSH` 工作区。本文是技术论证和有界试验方案，不是已经运行的自主迭代系统。

## 1. 明确结论

**可以构建“基于真实失败、由不同任务实施和验证、只接纳有证据改进”的有界迭代。当前不具备证据支持立即开启长期无人值守自优化，也不能保证每次尝试必然改善。**

如果要求“无需固定目标、无需真实验证、每轮必定产生有效改进”，答案是**不能**。复杂软件修改可能失败，也可能权衡后不值得做；任何承诺每次必改善的机制都容易通过改指标、重复包装或隐藏失败达成假成绩。

可实现的承诺是：**每轮必须产生可核验结果；只有满足预先固定验收条件的变化才进入已接受基线；无收益就拒绝并停止。** “尝试了一轮”与“完成一次有效改进”分别统计，不能用改名隐藏失败率。

目前技术可实现性有明确依据，经济价值仅有合理假设，尚未经过对照试验。建议先做一个受控试验，未通过前不开持续 loop。

## 2. 核查依据与可信度

本轮直接读取已安装 `resources/runtime/primary-runtime/runtime.json` 和 `app.asar` 内相关包的 README。当前安装版本 `0.2.1-rc.5`，捆绑 Node `24.21.0`；本轮测试实际使用环境 PATH 中的 Node `26.7.0`，两者不同，不能将当前测试当成捆绑 Node 已验证。

已保存 [能力审计与原始包契约](../../artifacts/requirements-loop-feasibility/20261104-capability-audit/audit.json)。审计脚本可复跑，不读取凭据、不启动模型、不重载插件。

| 能力/限制 | 本轮证据 | 判断 |
| --- | --- | --- |
| fresh spawn 子任务 | 安装包 `dsh-subagent-spawn-in-process` 契约：空白会话、自包含任务、独立工具作用域 | 能减少完整历史复制，适合聚焦实施与新视角验证 |
| fork 子任务 | 安装包 `dsh-subagent-fork-in-process` 契约：继承已完成轮次，当前进行轮次不继承 | 适合确需历史的续作；不宜作为所有审查的默认方式 |
| 回收结果与生命周期 | `startActivation`、结果 promise、取消/清理、结构化结果契约 | 可建立明确任务终点，不能把启动成功或 idle 当交付成功 |
| 后续消息与中断 | `send_message`、`interrupt_agent`、`list_agents` 契约 | 可以定向补充与停止；消息被接受不等于工作完成，中断被接受不等于子孙和进程已安静 |
| 深度/容量限制 | 默认 maxDepth=1，maxActiveSubagents=8；容量不限制累计 token | 可防递归失控的一部分；不自带本任务的成本闭环 |
| 权限隔离 | 子任务继承权限根，cwd 不缩窄权限；spawn 不继承父 agent-local 工具限制 | 不能仅凭“只读 reviewer”提示词声称技术隔离；需明确 preset/沙箱/验证器边界 |
| Worktree | 安装包存在，但官方工具是可选且默认关闭；从 commit 建立，不复制任何未提交/未跟踪内容 | 不可假设现已启用；当前工作区大量未提交变更，直接从 HEAD 开新工作树会漏掉现有成果 |
| 可执行检查基础 | 本轮三个现有测试文件：45 passed / 0 failed，约 18 秒；列出的源码哈希测试前后无变化 | 局部契约可自动验证，有短反馈基础；不是全量、真实宿主或多智能体实测 |
| 真实执行载体 | 当前插件使用 `ctx.get('agents')`、followup、whenIdle；[历史宿主探针](dsh-host-services-spike.md) 有真实工具执行记录 | 宿主执行并非仅模型聊天；历史单载体成功不证明当前多智能体设置已可用 |
| 当前端到端不足 | [真实 Desktop 尝试](../../artifacts/requirements-detail-v4/20261104-1357-real-host/report.json) 在身份边界 401，realAIExecuted=false | 认证通路未解决前，不可声明当前真实闭环可全自动运行 |
| 当前 v5 验证范围 | [v5 交接](../../artifacts/requirement-description-v5/2026-11-04T06-04-41/codex-handoff.md)：34 个 mock UI 断言，未调用真实模型/宿主 GUI | 可作为局部回归资产，不能充当真实意图到交付的证据 |
| 跨进程与崩溃恢复 | subagent 契约明确：进程本地所有权、无持久父邮箱、accepted-but-unlogged 消息可丢失 | 无法假设“退出 Desktop 后还会可靠自动迭代”；需检查点和失败后核对，不盲目重发 |

本轮没有在真实 Desktop 创建子任务、执行并发隔离测试、探测当前启用工具清单或消耗 DSH 模型调用。包已安装/基础组合有挂载行，不代表当前特定父会话中对应工具一定暴露且可用。

## 3. 多智能体究竟在哪里有额外价值

普通“改代码→跑测试”单个 agent 已能做，多加几个角色不自动增加价值。这里仅保留两个可能值得付费的增量：

1. **减弱实现者自证。** 实现任务容易沿自己的理解补断言；新会话验证任务从既定用户行为与证据出发，尝试使改动失败，能发现接口、正文、UI 和执行输入之间的不一致。
2. **跨层调查可分工。** 当失败同时跨越澄清、保存、详情投影、执行和证据绑定，独立定位可减少单个长上下文丢线索。已经能由一个精确测试定位的问题，不需要并行调查委员会。

fresh spawn 只能降低历史解释的锚定与上下文复制，不能让同一模型的错误统计独立；换模型也不是正确性的证明。最终依据必须是冻结行为检查、实际接口/工具回执和可复核结果。

不默认采用三人投票、角色辩论、逐轮全仓审查、让“产品经理 agent”持续发明新目标、要求 agent 相互夸赞或打分。不能为了证明多智能体有用，给已足够简单的问题强行拆任务。

## 4. 最小组织：一个调度者，两个有明确产物的任务

| 参与者 | 输入 | 允许产物与职责 |
| --- | --- | --- |
| 调度者 | 固定目标、当前已接受快照、客观失败、预算 | 选一个问题、派任务、核对证据、决定接受/拒绝/停止；不可自行改验收以放行 |
| 实现 agent | 失败复现、范围、不可改变的契约、代码快照 | 最小补丁、必要回归检查、影响说明；不为自己的改动签收，不修改冻结验收资产 |
| 验证 agent | 用户行为契约、相同复现环境、候选 hash | 独立操作和反例检查，提交实际失败/通过证据；不偷偷修代码再宣布实现成功 |
| 确定性验证器 | 固定命令、固定输入、只读验收资产、候选快照 | 执行并输出原始退出码/行为结果/hash；通过规则由程序判定，不能由自然语言“总体不错”替代 |

两个子任务优先用 fresh spawn，任务包自包含，不复制整段父对话。实现完成后才对固定候选执行验证；需要在基线先收集证据时，验证任务可先运行基线，再核对候选。没有必要不让它们反复通信讨论。

初始最多两个直接子任务，深度固定为 1，不允许递归组建团队。不是把宿主默认 8 个并发槽全占满。交互 UI 每次只有一个操作拥有者；两个 agent 同时控制同一桌面会产生不可归因的证据。

“确定性验证器”是脚本/隔离测试运行器，不应再由第四个大模型扮演。只有冻结检查无法覆盖的跨层、高影响修改，才按需增加一次专项审查；简单格式/样式变化不走整套模型评审。

## 5. 一轮必须怎样运行

### 5.1 冻结基线与可失败目标

从当前**有效工作区内容**生成隔离快照，包含本任务所依赖的未提交和新文件，记录清单/hash；排除凭据、大型历史证据和无关产物。不可只 checkout HEAD，也不可覆盖/提交/清理主工作区现有改动。列明依赖和运行版本；运行中来源若变化，重建快照或判作无效试验。

一轮只选一个当前已复现问题或一个可量化体验目标。先写可观察的失败条件，用相同检查在 baseline 上得到真实失败。仅凭旧报告、截图猜测或 reviewer 建议不能进入实施。

新发现问题的检查可在基线阶段补齐，但必须在候选实施前冻结，由验证侧保管。业务 AC、权限和证据规范不可由实现侧降低。测试错误要单独纠正并重新建立前后基线，不能当产品改进得分。

无法复现的发现先记 suspected；“没复现所以关掉”不是已修复。环境故障先归因；认证 401 不通过假 actor、复制 token 或降鉴权解决。

### 5.2 实施与独立验证

1. 实现任务只在候选副本写入，保留测试与需求约定。每轮最多一个问题的一组相关改动。
2. 完成后固定候选快照 hash，确认实现任务及其工具进程停止写入。
3. 确定性验证器运行冻结复现检查与相关回归；验证任务从真实用户步骤/反例做补充，读取完整原始回执。
4. UI 修改验证真实插件入口；mock 可作局部快速检查，但真实宿主层未测就明确未测。模型改动验证真实模型采样，不能用固定回答 mock 证明澄清质量改善。
5. 将 before/after、补丁、AC 结果、失败尝试、环境身份和资源成本绑定到同一 round/candidate。

候选只在以下条件**同时满足**时接纳：

```text
基线有可信失败或未达标测量
AND 同一冻结检查在候选上达到预定目标
AND 相关回归无新增失败
AND 范围、权限、需求/验收基线未被降低或偷换
AND 验证期间候选与证据身份一致
AND 所宣称层级有对应真实证据
```

回归中既有失败可以单独标注，不要求先修完整历史仓库；如果影响到本轮结果解释、认证或重要安全边界，则本轮不能接受。检查 timeout/unknown/flaky 不当成 pass。

### 5.3 接受或拒绝，不强制制造下一轮

有效候选才成为下一轮基线，保留原基线与拒绝候选。拒绝时丢弃的是该隔离候选，不用 `git reset --hard` 回滚共享工作区。

验证发现可定位缺陷时，可在本轮预算内给实现任务一次修正；再次失败则记 rejected/blocked，停止同一问题的循环。无新实质进展不再发“请继续优化”。

有价值的新问题入待办，但不能因为 agent 能提出问题就自动无限扩充范围。目标已满足、预算到达、需要真实业务决定或真实宿主不可验证时停止。阶段性局部通过不冒充完整 E2E。

## 6. 防止“自己改自己、自己证明自己”

插件是本次被改对象，**迭代控制、冻结验收、成本台账和证据归档放在它的可写范围之外**。不先把一个拥有所有权限的“自我优化后台”塞回需求插件。

实施隔离必须覆盖以下边界：

- 单写者：每轮只有一个实现任务修改候选。验证从固定候选的副本运行；测试的临时写入在测试目录，不修改被验证源文件。
- 验收保护：实现任务不能写冻结用例、验收规则、调度器或已归档证据。通过实际 sandbox/preset/运行器强制，不能仅靠提示词要求“请勿修改”。有 shell 工具时也要受相同文件策略约束。
- scope 核验：spawn 的父 agent-local 限制不会自动导入，显式选择并验证工具/preset。子任务 cwd 指向隔离目录不等于失去主仓库访问权。
- 测试代码是候选的一部分：即使测试运行器不使用 LLM，候选代码仍可能写文件或影响运行器；证据接收与冻结资产应受外部运行边界保护。无法强制这些边界时，只能做有人监督的候选分析，不能宣称可靠无人值守迭代。
- 运行隔离：被测插件使用独立 profile、端口、数据目录和测试需求；同一持久化存储不让两个宿主并发写。正式 Desktop 不用于每轮热重载实验。
- 停止确认：`interrupt_agent` 接受请求后仍需等待真正静止；必要时按已记录句柄 dispose 并回收准确的子孙/测试服务。不能用误杀所有 DSH 进程的方式清场。
- 自身修改：候选不能修改当前 loop 的预算、验证定义和评分规则。更新这些规则是独立任务，重新建立基线。

本地 worktree 是代码隔离便利，不是权限或执行隔离。官方工具默认关闭，只负责创建；当前若未启用，可在已授权范围内使用普通隔离副本或现有 Git 工具，不为试验改正式配置。候选提升为主工作区改动也应逐项核对来源版本，不自动发布或签收。

## 7. 成本与价值如何证明

### 7.1 当前值得试验的原因

需求插件已经有多个真实能力接点：澄清、确认保存、正文解析、UI 投影、执行恢复与证据绑定。历史上出现过“单测通过但真实路径卡住”“旧决策重新出现”“展示与来源格式不一致”等跨层问题。这类任务比纯样式润色更可能从独立验证受益。

但 v4/v5 正在持续变化，旧缺口已有部分修复。本轮三个测试文件 45/45 通过，v5 已有文档契约与接口测试，不能再把“新增这些能力”当成未完成任务。现有 mock 成绩也不能计作本轮新增收益。

### 7.2 先证明循环有效，再证明多 agent 值得

分开做两层判定：

1. **机制验证**：选择一个当前可复现、范围明确的问题，验证 baseline fail → candidate pass、无回归、失败不提升、取消能收口。这个试验可以证明机制能运转，不能证明多 agent 比单 agent 更省钱。
2. **价值对照**：最多选择两个不同类型的实际问题，分别从同一快照开展“单 agent + 同一验证器”与“实现/验证两个任务 + 同一验证器”的配对试验。相同目标、权限、工具、预算和判定规则；条件允许时对调执行顺序，隔离历史和候选，禁止后跑路径直接读取前一路径答案。

没有双路径预算时可以先做机制试验，但结论必须停留在“技术可行，额外收益未证”，不以一次成功宣布经济性成立。两组小样本只用于本项目采用判断，不是普遍统计证明。

记录全部角色与重试的：input/output/cache token、实际提供方计费口径、调用数、耗时、人类实际介入分钟、确认修复的独立问题数、新增回归、接受/拒绝次数。缺成本数据就标 unknown，不只汇报最终成功那一次。

比较指标优先顺序：

1. 同一固定业务目标是否达成，是否新增回归。
2. 验证任务是否发现了实现者漏掉、可复现且影响验收的问题，或显著减少人工追查。
3. 每个已接受改进的全成本和人类介入是否符合事先约定上限。

经济性可按用户自己的时间价值估算：`额外验证价值 ≈ 节省的人工时间价值 + 避免返工的保守价值 − 新增模型/运行/协调成本`。避免返工价值无法估计时按 0，不能编造 ROI。

如果单 agent 使用同一验证器已同样完成，独立任务没有额外发现、没有减少人工，反而增加成本或时延，就选择单 agent。若主要收益来自新增测试，应如实归因给测试资产，不能全部归功多智能体。

### 7.3 有界试验的建议初值

以下仅是供执行前采用/调整的试验参数，**不是当前宿主自带的已验证硬限制**：

- 每次试验最多 3 轮候选，最多接纳 2 个独立改进，嵌套深度 1，最多 2 个直接子任务。
- 同一候选最多一次定向修正；连续两轮拒绝/没有新增有效证据就停止。
- 在执行前设总 wall-clock 与真实计费预算；可先讨论采用 45 分钟时间盒，成本上限须根据实际模型价格和任务规模确定，不在缺报价时虚设收益承诺。
- 宿主的子任务容量和输出 token 上限不是累计费用上限。需要外部台账在派发前检查，计入父任务、子任务、系统提示和缓存计费；在途请求预留余量。当前若没有可靠实时用量，不承诺严格 token 硬封顶，可用较少固定调用与外部超时先限制试验，并明确费用上界未知。
- 不进行模型“保持思考”轮询。使用生命周期通知/结果 promise，等待期间不重复问状态；读日志和测试优先用程序，不让模型重新总结每行输出。

机制失败、认证无法完成、边界无法隔离、成本不可接受，都直接停止，不用追加 agent 试图掩盖。

## 8. 现在怎样选第一轮

先在隔离副本以当前构建复现，不直接选早期报告里的已修问题。候选方向按证据成本排序：

| 方向 | 值得检查的用户结果 | 本轮是否已证明缺陷仍在 |
| --- | --- | --- |
| 描述链路 | 一次澄清回答是否真正进入最终 FR/AC，确认前后与执行读取是否一致 | 未证明；本轮局部测试通过，真实模型/宿主链路仍需验证 |
| 决策与运行 | 回答后是否续同一运行，idle 是否正确收口，是否重复问旧问题 | 有历史问题与修复，当前需复现，不能预设仍坏 |
| 详情状态 | 当前事项与后端执行事实是否一致，是否同时出现互斥文案 | 用户截图有线索，当前构建需定向复现 |
| 主观美观 | 用户是否觉得直接、舒服 | 不适合让 agent 自评达标；必须真实用户观察，pending_human 不是循环失败也不是通过 |
| 历史 task-list 业务 AC | 冻结夹具是否满足搜索/筛选要求 | 属于另一业务夹具，不自动变成当前插件优化范围 |

优先把“是否真实贯通”补成可验证路径；若认证阻塞先明确需要何种合法 UI/测试身份通道，不能降身份校验、伪造人类或把 mock 改称实测。根因确实需要真人操作时如实等待，不能要求 loop 绕过它。

模型相关目标用固定业务意图与答案集评估，不以随机回答自相满意。一次样本只能证明一次成功；比较澄清收敛需预先约定有界多样本、轮次与重大决定不丢失约束，承认模型随机性和有限预算。UI 可用性只自动验证可操作部分，不给“乔布斯/马斯克评分”。

## 9. 执行前必须满足的准入项

这些不是让用户每轮重复点确认，而是在已有授权范围内由 DSH 做一次真实探针并给事实：

1. 当前父会话能发现可用 spawn/control；fresh 子任务实际能读隔离文件、返回结构化结果，并可可靠停止。新任务必须验证所需工具存在，不能只凭包 README。
2. 隔离副本含当前有效代码；候选、验证资产、证据与正式业务数据的写入边界得到实际验证。
3. 对本轮对象至少有一个真实可失败的检查；所需宿主/浏览器/模型通路合法可用。UI 操作能力不假设会自动传给任意子任务。
4. 预算、停止条件、基线提升规则由候选之外的控制器落实；崩溃后按持久检查点核对，不能假设消息 exactly-once。

缺一项，本轮不能启动对应层级的无人值守修改；可继续只读定位或有人监督的小范围试验。最小控制器只需执行固定任务协议和账本，不先造一个新的多智能体管理平台。

## 10. 如决定试验，交给 DSH 的任务边界

> 对当前需求插件开展一次有界多智能体优化试验，不做长期后台自优化。先按本文准入项探测实际能力，建立含当前未提交成果的隔离快照，选择一个当前可复现问题并冻结验收。使用一个 fresh 实现任务与一个 fresh 验证任务，深度 1、单写者；固定脚本根据相同 baseline/candidate 检查裁决。冻结验收、台账与归档处于实现可写范围之外。无可信失败、不支持实际隔离、认证阻塞、无进展或预算达到则停止，明确报告。只有严格前后对照改善且无相关回归的候选才能提升基线。不要更改业务 AC、放宽权限、自动签收/发布或给旧运行补推定授权。机制试验通过后，只有需要证明多智能体增益且有预算时，进行与单 agent 使用同一验证器的配对比较；否则结论保持“收益未证”。

每轮输出 `round.json`：目标、基线/候选 hash、冻结检查 hash、角色/session ID、执行与工具证据、before/after、回归、资源成本、accept/reject/blocked 及原因。只用数据生成总览 HTML，给 Codex 的 handoff 指向原始日志和补丁；失败轮也保留，报告与业务授权分开。

## 11. 本轮交付的准确含义

本轮完成已安装包能力核查、当前报告与源码复核、三个现有测试文件执行，并形成以上可行性/价值方案。**没有启动 DSH 自迭代、没有创建 DSH 子任务、没有证明当前多任务隔离或经济收益。**

因此当前决策是：**值得做一次严格有界的机制试验；不值得直接开启无限 loop。若无法提供受保护的行为验证与实际成本数据，就不能声称满足用户要求的“切实可行且每轮有效”。**
