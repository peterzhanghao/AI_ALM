# 需求详情：执行过程与三页签重构设计

日期：2026-11-05。状态：开发设计已转为实施中；代码、隔离回归和任务状态见 `docs/analysis/clarification-and-execution-refactor-tasks-20261105.md`。范围是需求详情的「需求正文 / AI 进展 / 历史记录」及其运行观察接口，不改变验收、发布或执行授权规则。

## 目标与边界

- 需求负责人能看到本次交给 AI 的内容、进展、需要决定的事项与交付结果；开发者可按需查看工具调用及结果。
- 以现有 DSH 会话及其事件为事实来源；统计只在可归属时展示，缺失值为未知。不可将 AI 自述当作测试或人工验收通过。
- 沿用宿主的主题变量、排版与交互组件，匹配 DSH 对话页面的紧凑操作密度；不复制附件中的数据或固定美元单价。
- 可展示供应商实际返回的可见推理摘要；内部推理未提供时明确不可用，不生成冒充真实推理的解释。
- 现有运行在宿主重启后可能转入新会话。不能把单个 `run.sessionId` 当作完整历史；旧数据无法证明关联时显示历史不完整，禁止猜测归属。

## 交互设计

### 共用框架

顶部保留返回、需求编号、标题、状态和唯一主操作；低频及危险操作在更多菜单中，保留确认与权限规则。页签固定为「需求正文 / AI 进展 / 历史记录」。小面板内标签可横向滚动；滚动区域和顶部、底部操作不遮挡键盘焦点。各页共享状态模型，不复制可产生不同结论的判断。

### 需求正文

先显示目标、范围、功能和验收标准，再显示约束、来源及待确认问题；保持原文版本和来源可追溯。当前业务决定与主操作就近显示；技术状态链接到 AI 进展而非展开完整日志。编辑草稿在切页、关闭、浏览器离开时沿用明确的未保存保护。

### AI 进展

顶部显示运行状态、阶段、最近活动、需求版本、当前阻塞和必要的回答/恢复/取消动作。下方同级视图为：

1. **对话**：按时间展示输入、人工回答、AI 可见回复、最终结果；明确会话段、恢复边界及未完成消息。允许查看完整输入，避免在默认视图反复打印系统提示。
2. **轨迹**：工具名称、目标、状态、时间、结果摘要；按需展开命令和输出，支持截断说明、继续加载与复制。失败和等待决定优先可见，执行结果只陈述可验证事实。
3. **用量**：以运行、会话段、模型和阶段为范围；展示请求数、输入/输出、缓存读取/写入、压缩情况、代理提供的上下文节省估算、费用估算及数据来源、更新时间、覆盖范围。部分数据明确「不完整」；无数据为「未知」，不显示 0 或虚构的节省额；代理节省估算明确标记为非账单。

优先提供宿主原生会话入口；须先验证指定会话的导航 API。数据不可用时仍保留运行状态、验收证据和可用的会话入口。用户阅读旧消息时不强制滚到底，提供「回到最新」。

### 历史记录

以带时间和来源的业务时间线开始，区分需求变更、运行、验证、人工验收和发布。点击条目到相关运行或证据；当前需求的多次运行分别可选，不混入其他需求。归属、关联、GitHub、缺陷和技术来源独立折叠，不把摘要当完整审计日志。

## 数据与接口设计

1. **会话关联**：在运行记录中追加有序 `sessions[]`，每段包含 `sessionId`、创建时间、结束时间、原因、来源和需求版本；保留现有 `sessionId` 兼容当前读取。创建或恢复会话成功后与 run 更新一起持久化；处理写入失败、重复重试及并发恢复。迁移只将可证实的当前 ID 加入，旧段未知明确标记。
2. **读取模型**：服务端从 root + requirementId + runId 解析授权范围，再按关联 sessionId 调用宿主服务。不要接受客户端任意 sessionId 直接读取。使用宿主受支持的 session/query 接口，先验证持久化回放能力、事件类型、保留期和跨重启行为；不可依赖私人文件格式。
3. **事件投影**：事件统一为 `{sessionId, seq, at, kind, status, summary, detailRef}`；`(sessionId, seq)` 去重、顺序稳定；保留未知事件而不伪造内容。历史分页与实时订阅共用游标，断线后重放，避免重复和漏消息。实时片段为临时态，持久化事件为回放依据。
4. **用量归属**：先验证宿主 usage 事件及 billion-context 查询契约、会话 ID 对应方式和代理运行状态。以请求 ID 或可验证的会话段去重；区分主会话、子会话、独立 `llm.stream` 评审与压缩调用。无法关联的调用不并入总计；显示已覆盖/未知范围，缓存读写口径及费用来源。价格按提供方、模型和时间版本记录；估算不冒充账单。
5. **访问与性能**：后端对日志中的凭据、令牌和敏感字段按已有策略处理；对话、工具明细和大输出按需分页并限额，Markdown 使用安全渲染。客户端对长列表采用虚拟化或分段加载，后台合并高频流更新；不把完整历史放进需求列表查询。
6. **状态**：覆盖无运行、排队、运行、等待输入、失败、取消、结束、恢复、宿主不可用、历史过期、部分日志、流断开重连，以及主题和窄面板；状态取真实运行和事件，未知不得标为成功。

### 澄清页实施补充

需求澄清页与需求详情共用运行和证据边界，本轮新增实现要求：

1. 输入、分析、回答、候选、确认和回执阶段继续使用同一个 `ModalShell`，但弹窗标题通过 `aria-labelledby` 关联，分析阶段以 `aria-busy` 暴露，弹窗滚动链使用 `overscroll-behavior: contain`。
2. 原话、聊天记录、问题回答、候选字段、验收行、负责人和优先级均有稳定 `name`；动态提示使用 `role=status` / `aria-live=polite`，图片预览有尺寸和文本替代，移除控件满足可触控尺寸。
3. 确认页默认突出问题/目标、去向和门禁原因；范围/未证实部分按需展开；写入产物和权限信息在不影响必填优先级门禁的前提下按需展开。服务端确认、幂等、草稿保存和人工验收规则不变。
4. 澄清页验收必须同时覆盖真实 Desktop AX 树、隔离浏览器窄屏/放大、未保存保护、分析/回答失败和真实输入后的读屏与主题行为；空弹窗截图不能作为完整视觉验收。
