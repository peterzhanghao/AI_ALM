# REQ-ALM-014 需求澄清判决式重构与运行时缺陷自愈

## 目标
把需求澄清从表单填报改造为带证据的判决流程，并让需求插件在运行期遇到缺陷时自动采集、分类、自愈与验证，不再依赖人工复制粘贴报错。

## 问题与场景
近 20 次澄清会话中 17 次模型调用失败，Grill 澄清 0 次生效；失败后由关键词规则回填伪草稿且仍可确认入库；失败不写入 .alm/failures，因此插件既无法澄清清楚，也无法自我修复。用户遇到缺陷时只能手工复制报错到主对话。

## 验收要求
- AC-01澄清链路的 5xx 失败必须写入 .alm/failures，带 runId、model、timing 与去重指纹，重复失败累加 occurrences。
  - 前置：准备一个会返回 5xx（或不可达）的模型路由，并记下它的 provider / 模型名。
  - 动作：在需求插件的澄清入口输入一段需要澄清的业务诉求并提交分析；让同一个失败连续发生两次。
  - 预期：两次都提示没有拿到模型结果且不写入需求；.alm/failures 只新增 1 条 FAIL 记录，含 runId、model、timing 与去重指纹，第二次仅 occurrences 加 1。
  - 判定：核对失败记录的四个字段与 occurrences，并确认需求列表没有新增条目。
- AC-02首 token 超时与输出超时两类缺陷必须能被自动分类，并通过调整自愈策略参数后重跑同一会话，验证首 token 到达且分析成功。
  - 前置：准备一个会挂起、不返回任何分片的模型路由；可把自愈策略的首 token 预算临时调小以缩短等待。
  - 动作：用该路由提交分析，等待首 token 看门狗触发超时；随后在同一澄清会话点「重试分析」。
  - 预期：第一次运行被归类为首 token 超时（不是“模型乱答”）；.alm/self-heal/policy.json 的首 token 预算被上调并留有 history；第二次运行成功且 timing.firstTokenMs 有实测值。
  - 判定：查看会话运行记录的分类与 timing、以及策略历史的 revision / before / after，确认没有改源码。
- AC-03模型未参与时不得生成 problem 与 acceptance，界面必须显示未澄清且禁止一键确认。
  - 前置：模型选择处于无模型或不可用状态。
  - 动作：输入任意需求文本并提交分析。
  - 预期：界面显示「未澄清」，problem 与验收为空，一键确认按钮不可点；仓库里没有新增需求文件。
  - 判定：核对界面提示、字段为空、确认按钮禁用，并检查需求列表。
- AC-04判决必须落在八种结果之一（create/extend/revise/merge/split/decline/defer/answer），缺少必要条件的判决不得入库。
  - 前置：已存在至少一条需求；准备八类诉求各一句（新建、追加、修订、合并、拆分、延后、拒绝、答疑）。
  - 动作：在同一澄清入口逐条提交，每次查看判决卡与去向。
  - 预期：每次判决落在 create / extend / revise / merge / split / defer / decline / answer 之一；缺必要条件（例如合并未选择目标需求）时不能入库。
  - 判定：对照判决卡的去向与是否生成需求，确认没有越界写入。
- AC-05拒绝必须写入否决账本并可被后续查重命中，包含理由、替代方案与再提触发条件。
  - 前置：一条此前被拒绝的诉求，已登记理由、替代方案与再提触发条件。
  - 动作：再次提交同类诉求。
  - 预期：命中否决账本并显示上次理由与再提条件，不直接新建需求。
  - 判定：核对否决记录与查重命中提示。
- AC-06自愈策略只允许调整参数与模型链，不得修改源码；每次策略变更必须可回滚并记录历史。
  - 前置：触发一次可自愈的超时（同 AC-02）。
  - 动作：查看自愈策略历史，并回滚到上一个 revision。
  - 预期：变更只涉及参数与模型链；history 记录 actor / reason / before / after；回滚后参数恢复且记录继续追加，源码无改动。
  - 判定：对比策略文件前后内容与工作区改动，确认源码未变。
