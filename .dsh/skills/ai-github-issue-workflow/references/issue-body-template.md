# Issue 正文模板

> 由 `ai-github-issue-workflow` 按需加载。内容必须针对该 Issue，不能把同一段模板复制给多个子项。

```markdown
## 目标与上下文
本切片在发布链或执行链中的位置、上游可复用成果、下游消费者。

## Parent
父 Issue 的真实链接；尚未发布时写 ALM 规划键并标明“待同步”。

## 实施范围
- 涉及模块：准确目录或服务。
- 本次交付：可观察的实现结果。
- 依赖：需要先完成的 Issue（同时用 blocked-by 关系表达）。
- 外部依赖：第三方服务、凭据或环境；没有写“无”。

## 来源与范围
需求来源、设计文档或 ADR，以及此处选择复用或偏离的理由。

## 先读
3～5 个准确的章节、契约文件或已合并 PR（含固定 SHA）；不能只填文档名。

## 接口与数据
输入输出、状态与事务边界、兼容性与迁移方式。

## What to build
列出可观察的实现结果、关键数据流和各接口或事件的行为。

## Out of scope
相邻能力及其承接 Issue；不要把范围写成“顺手重构”。

## 交付物
- [ ] 可独立检查的实现或文档产物。

## 验收与证据
- [ ] 正例：输入、输出和可观察结果。
- [ ] 反例：越权、错版本、非法状态、失败或恢复行为。
- [ ] 测试落点：新增/修改的测试文件、夹具路径或用例名。
- [ ] 测试命令、固定 SHA、截图或环境证据位置。
```

## 填充要求

- 「先读」必须是可定位的章节、契约文件或带固定 SHA 的 PR，写文档名视为不合格。
- 「验收」必须成对给出正例与反例，并写清测试落点；只有正例、或没有测试落点的 Issue 不满足交付标准。
- 「Out of scope」写清相邻能力由谁承接，避免范围蔓延。
- 禁止出现“按需求开发”“测试通过”这类无法验证的表述。
- 接口与字段沿用已有契约；差异项显式标注并走设计评审。
