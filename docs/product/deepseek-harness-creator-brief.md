# DeepSeek Harness 创造模式实施 Brief

将本文件和 [`ai-native-alm-mvp.md`](ai-native-alm-mvp.md) 一起提供给 DeepSeek Harness Desktop 创造模式。目标是产出可运行、可测试的 MVP 原型，不只生成静态产品页面或方案文档。

## 创造任务

请在当前工作区构建一个 AI Native ALM MVP：DeepSeek Harness Desktop 中有独立的需求插件和架构插件，两者共用研发资产、工作区、变更集和门禁能力。实现“订单支持部分退款”的端到端样例，支持本地分支修改、确定性检查、差异/影响审阅、PR 门禁和可重建发布基线。

完整需求、边界、数据模型、架构、权限规则和验收以 `ai-native-alm-mvp.md` 为准。先读它和仓库 `README.md`、`docs/development/github-workflow.md`。实施前检查 `git status`，保留现有改动。

## 必须遵循的实施顺序

### 1. 验证宿主能力

- 确认当前安装的 DeepSeek Harness Desktop 版本、插件 SDK/示例、许可证与插件打包方式。
- 使用该版本的真实接口验证：插件发现与启停、工具注册、插件服务依赖、UI 扩展/slot、权限提示、错误恢复。
- 不猜 API 名称，不用伪造的宿主对象或占位组件冒充已集成插件。
- 先产出一个可安装的最小插件和验证记录。若某扩展点不可用，明确记录限制，继续实现独立 core CLI/API，并将插件集成限制封装在适配层。

### 2. 固定最小领域契约

- 以仓库文本文件作为唯一可编辑事实源；StrictDoc 负责需求结构，Markdown/ADR、YAML、OpenAPI、Mermaid 负责架构与验收资产。
- 为需求、模块、ADR、接口、数据模型、验收测试定义稳定 ID、Schema 和关系类型。
- 建立部分退款小型样例仓库，至少包含一条需求、一个架构决策、一个接口/数据定义和一条验收测试。
- 记录每次检查的源 SHA、目标 SHA、规则版本、工具版本、结果与产物哈希。

### 3. 实现共享核心和插件

- 先实现可独立测试的 core：工作区、资产读取、ID/关系索引、diff、影响闭包、硬门禁、基线清单。
- 再实现需求插件与架构插件。两个插件必须通过同一个 ChangeSet 和 core 服务协作，不复制资产状态或创建两套审批。
- Agent 工具遵守最小权限：默认只读，写操作限制在当前工作分支；无工具可以批准自身变更、修改门禁、保护规则或发布存储。
- UI 呈现可审阅的清单、详情、结构化差异、影响项和门禁证据。不要用静态 mock 代替实际数据流。

### 4. 接入评审、集成和基线

- 先以本地 Git 仓库和可重复脚本跑通流程，再接入 Gitea PR/Runner。
- `develop` 合并要求服务端必需检查和人工审批；候选 SHA 改变时旧审批失效。
- 合并后生成开发预览。发布审批通过后生成不可覆盖基线：源 commit、规则/工具版本、审批、门禁结果、文件列表、SHA-256。
- 失败重试必须幂等；发布包重建失败时不得生成正式基线。
- 本阶段不迁移 AI_ALM 当前 GitHub 仓库，不新增公网 StrictDoc 服务。

## 交付物

- 两个可安装的 DSH Desktop 业务插件及共享 core；若宿主能力受阻，交付插件适配原型和可运行 CLI/API，并列出未完成的宿主集成项。
- 部分退款样例资产及格式/关系 Schema。
- 确定性门禁、差异和影响分析实现。
- 本地开发/验证环境说明与可重复启动脚本；Gitea/Runner 配置样例（凭据使用环境变量或 Secret，不提交真实密钥）。
- 单元、集成、插件契约、端到端与负例测试。
- `docs/` 中的架构、运行、权限、升级、备份/恢复说明，以及实现决策 ADR。
- 一份验证报告：实际 DSH/Gitea/StrictDoc 版本、运行命令、测试结果、截图或日志引用、已知缺口和复现步骤。

## 强制验收用例

1. 正例：从指定基线创建部分退款变更，同时更新需求、架构/接口和验收资产，所有门禁通过并形成 PR。
2. 负例：重复 ID、悬空关系、缺少验收条件、非法格式分别被稳定拦截，错误定位到资产 ID/文件。
3. 审批：人工批准 SHA-A 后推送 SHA-B，SHA-A 的审批不能满足合并门禁。
4. 权限：Agent 不能批准自己的变更、修改保护规则/门禁策略或覆写已发布基线。
5. 发布：批准后可生成不可变清单；从相同 commit 重建，文件清单和 SHA-256 一致。
6. 故障：CI 中断或收到重复回调后可重试，不产生重复发布、不丢失证据。
7. 宿主：在记录的目标 DSH Desktop 版本中真实安装、启用、使用并关闭插件；不得只用单元测试宣称插件兼容。

## 工程约束

- 先给出短实施计划和拟修改文件清单，再按阶段实现；每阶段运行相应测试。
- 采用目标 DSH 仓库的插件范式，保持插件与 DSH 适配器薄、core 领域逻辑可独立测试。
- 所有业务硬规则用确定性代码检查；AI 语义审查必须给出证据引用，结果不能绕过硬门禁。
- 对外部写操作使用最小权限；不提交凭据；写入后回读并核对。
- 不覆盖用户现有文件或未提交改动；不虚报测试、实际宿主验证、兼容性或完成状态。
- 任何未满足验收项都留在验证报告中，并说明复现方式和风险。

## 创造模式最终回报格式

完成后说明：实现了什么、插件如何安装/运行、实际验证的宿主与依赖版本、通过/失败的测试命令、正反例结果、发布基线重建结果、未解决问题。列出关键文件的相对路径，并给出启动和验证命令。
