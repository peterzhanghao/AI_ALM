# 从产品蓝图到 AI 可执行任务：技能化方案

- 状态：评审草案
- 日期：2026-10-23
- 关联：[需求评审](../analysis/alm-mvp-requirements-review.md)、[架构](architecture.md)、[ADR 0003](../adr/0003-alm-mvp-engineering.md)

## 1. 问题：蓝图不能直接交给 AI 执行

产品蓝图描述的是**能力**（“需求插件能查看追踪缺口”），而 AI 执行需要的是**动作 + 判定**（“运行哪条命令、读取哪个文件、什么算通过”）。直接让 Agent 读蓝图开发，会得到三种不可控结果：自行发明目录与接口、验收标准各写一遍、上下文一换就重来。

转化的本质是三步：

```text
能力（可描述） → 契约（可判定） → 技能 + 任务卡（可执行、可复现）
```

- **契约**：数据形状、命令、退出码、证据字段、权限边界。契约是人和 AI 的共同接口。
- **技能**：稳定知识。目录结构、命令用法、规则表、模板、故障诊断。技能属于产品/仓库，不随任务变化。
- **任务卡**：本次增量。范围、正例、反例、证据命令。一卡一 PR。

## 2. 两层技能：产品技能与开发技能

“AI 原生 ALM”意味着 AI 既是**构建者**也是**使用者**，所以技能分两层：

| 层 | 技能 | 使用场景 | 载体 |
|---|---|---|---|
| 产品技能 | `alm-change-workflow`、`alm-requirements`、`alm-architecture`、`alm-release-verify` | 终端用户的 Agent 在 ALM 仓库里改资产、过门禁、提 PR、核基线 | `packages/alm-skills/*`，安装到目标工作区 `.dsh/skills/` |
| 开发技能 | `alm-mvp-dev` | 构建/维护 ALM 本体的 Agent：布局、命令、测试、契约、进度约束 | 本仓库 `.dsh/skills/alm-mvp-dev/` |

这两层不能合并：产品技能的读者是“在业务仓库里干活的 Agent”，开发技能的读者是“在 AI_ALM 仓库里写代码的 Agent”。合并会导致产品技能泄漏构建细节，开发技能被业务规则淹没。

## 3. 转化流水线（7 步）

| 步骤 | 输入 | 动作 | 输出 |
|---|---|---|---|
| 1. 能力原子化 | 蓝图章节 | 每个能力写成“一个动作 + 一个确定性输出” | 能力清单（动词 + 对象 + 判据） |
| 2. 契约先行 | 能力清单 | 定义数据结构、CLI 命令、退出码、证据字段 | `packages/alm-core/src/contracts/*` + 命令表 |
| 3. 拆任务 | 契约 | 每张卡 = 一个可独立验收的增量 | `ALM-xx.yy` 卡片 |
| 4. 绑技能 | 任务卡 | 卡片引用技能，不复制技能内容 | 卡片“先读”字段 + 技能名 |
| 5. 门禁可执行 | 验收项 | 每条验收对应一条可运行命令或测试名 | 证据命令 |
| 6. 发布门禁 | 卡片 | 台账 `确认结论=确认发布` 才进 GitHub | 远端 Issue |
| 7. 执行与回写 | Issue | 技能加载 → 按卡实现 → 跑证据 → PR → 收口 | PR + 台账 |

### 3.1 第 1 步的判定标准

一个能力能进入任务卡，必须同时满足：

- 有确定的输入（仓库路径、基线 SHA、资产 ID）；
- 有确定的输出（退出码、JSON 字段、文件）；
- 有可复现的判据（命令 + 期望结果），而不是“体验好”“覆盖全面”。

不满足的（如“UI 易用”）留在评审清单，由人验收，不写成 AI 任务。

### 3.2 第 3 步的拆分规则

- 一卡 = 一人 + 一分支 + 一 PR + 一条可独立验收的路径。
- 超过约 1 人日，或需要改两个不相邻模块 → 拆子卡。
- 跨仓（产品仓库 / 样例仓库）→ 各建一卡。
- 卡与卡之间用 `blocked-by` 有向依赖，不用“先后顺序”描述。

## 4. 任务卡五要素

每张执行卡必须写全，缺一不发布：

1. **范围**：涉及目录/文件白名单，明确“不在范围”。
2. **接口**：输入输出、数据结构、命令、错误码。
3. **正例**：输入 → 输出 → 可观察结果（含命令）。
4. **反例**：越权 / 非法状态 / 错 SHA / 失败恢复，至少一条。
5. **证据**：可运行的测试命令、固定 SHA、环境或截图位置。

技能与卡片的分工：

```text
技能 = 稳定的“怎么做”（布局、命令、规则、模板、诊断）
卡片 = 本次的“做什么”（增量、边界、验收）
卡片只写：技能名 + 具体章节 + 本次差异；不复制技能原文。
```

这样技能升级不需要改历史卡片，卡片也不会因为复制而漂移。

## 5. 技能清单与验收

### 5.1 开发技能 `alm-mvp-dev`

| 章节 | 内容 |
|---|---|
| 仓库布局 | `packages/*`、`fixtures/*`、命令入口 |
| 常用命令 | `node bin/alm.mjs check/index/show/diff/impact`、`node --test`、`scripts/demo-init.ps1` |
| 契约位置 | 五类契约与版本规则；改契约必须升版本并更新测试 |
| 门禁规则 | 规则表、级别、如何新增一条规则（注册表 + 反例） |
| 交付纪律 | 一卡一分支一 PR；不夹带；不虚报；证据先跑 |
| 故障诊断 | 解析失败、样例仓库脏、插件未加载、证据哈希不一致 |

验收：DSH 能加载（`skill` 工具可调用）；文中命令在干净工作区可执行；任务卡引用的章节真实存在。

### 5.2 产品技能

| 技能 | 触发 | 关键约束 |
|---|---|---|
| `alm-change-workflow` | “改这个需求并提 PR”“建变更工作区”“跑门禁” | 只读默认；写操作限当前工作区；不得审批/发布/改规则 |
| `alm-requirements` | “拆需求”“补验收条件”“需求追踪缺口” | SDoc 子集语法、必填字段、关系选择、失败修复 |
| `alm-architecture` | “新增 ADR”“改接口”“看影响范围” | ADR/模块/接口/数据模型格式、Mermaid、影响闭包用法 |
| `alm-release-verify` | “校验基线”“重建发布包” | 只读；输出哈希比对结果；不得改写基线 |

验收：技能内的命令与 core CLI 一致（CI 校验）；权限描述与工具实际能力一致；含至少一条反例处理。

### 5.3 技能质量门禁

| 检查 | 方式 |
|---|---|
| frontmatter 合法、名称与目录一致 | `scripts/validate-skills.ps1` |
| 引用的命令真实存在 | 技能冒烟脚本：抽取 `alm *` 命令做 `--help` 检查 |
| 引用的文件/章节存在 | 链接检查 |
| 正文 ≤ 8 KB，长内容进 `references/` | 校验脚本 |
| 权限表述与工具一致 | 与 `alm-core` 工具清单对比（人工 + 测试） |

## 6. 能力 → 任务 → 技能 → 证据 映射

| 蓝图能力 | 任务 | 技能 | 证据命令 |
|---|---|---|---|
| 宿主插件可安装/启停 | ALM-01.02 | `alm-mvp-dev` | 安装记录 + 工具调用 + slot 可见 |
| 资产解析与稳定 ID | ALM-02.01 | `alm-mvp-dev` | `node --test test/unit/parse` |
| 部分退款样例 | ALM-02.02 | `alm-requirements`、`alm-architecture` | `alm index --json` 输出 7 类资产 |
| 确定性门禁 | ALM-02.03 | `alm-change-workflow` | `alm check` 正例 exit 0（`REN-002` 为 `pass` 或 `skip`）、5 类负例 exit 1 |
| 语义差异 | ALM-02.04 | `alm-change-workflow` | `alm diff --base SHA --json` 字段快照 |
| 影响闭包 | ALM-02.04 | `alm-architecture` | `alm impact --asset REQ-PAY-001` |
| 证据与基线 | ALM-02.05 / 04.03 | `alm-release-verify` | `alm baseline verify` 哈希一致 |
| 双插件协作 | ALM-03.02–03.04 | 产品技能 | 同一 ChangeSet 的两次插件操作记录 |
| 审批失效 | ALM-04.01 | `alm-change-workflow` | 旧 SHA 审批 → `APPROVAL-001` fail |
| 幂等 CI/发布 | ALM-04.02–04.04 | `alm-release-verify` | 重复回调不产生第二份基线 |

## 7. 反模式

| 反模式 | 后果 | 替代 |
|---|---|---|
| 把技能当产品文档写 | 触发不到、加载后无用 | 技能只写“怎么做”，描述前置触发词 |
| 任务卡复制技能正文 | 两处漂移，改一处必错 | 引用技能名 + 章节 |
| 验收写“测试通过” | 无法判定 | 写命令 + 期望退出码/字段 |
| 让技能承载权限判断 | 提示词可被绕过 | 权限在工具与门禁代码里，技能只描述 |
| 一个技能覆盖所有角色 | 上下文过载、触发模糊 | 按角色/阶段拆（change/requirements/architecture/release） |
| 先写插件 UI 再写 core | UI 造假、无法回归 | core + CLI 先行，插件薄适配 |

## 8. 实施顺序

1. **ALM-05.03 开发技能**：与工程骨架同批，后续每张卡都依赖它。
2. **ALM-05.01 变更工作流技能**：与 core 工具契约（ALM-03.01）同批，先只读、后写入。
3. **ALM-05.02 需求/架构技能**：跟随双插件（ALM-03.02/03）。
4. **ALM-05.04 技能一致性校验**：进入 CI，防止技能与 CLI 漂移。

技能不是“最后补的文档”，而是与代码同版本的交付物：改命令必须改技能，改技能必须跑冒烟。
