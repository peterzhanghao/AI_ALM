## 结论

设计合理，可以作为 DSH 的日常迭代方式：人在插件提出业务需求，DSH 执行修改、验证并形成候选，人确认业务效果。当前具备构建有界自我迭代流程的基础，且部分部署/GUI 验证链路已有实机历史证据；尚不能宣称实现稳定的无人值守、自恢复、长期自主优化闭环。

需求入口是被改产品本身，并不会形成无法实现的逻辑循环：运行中的旧版仍可管理需求，执行器修改下一版源代码；旧版安全交回后，由稳定部署组件负责切换并验证新版。问题集中在版本交接、失败恢复和独立判定，不在需求从哪里录入。

## 距离可靠闭环的缺口

1. **开发基线隔离与单写者**：当前执行器 cwd=root，不自动代表独立工作树。需求执行会话、Codex、人工同时修改同一源码，会使候选/授权/验收绑定失效。应基于包含当前未提交成果的固定快照产生候选，不能只从陈旧 HEAD 开工作树；验证及切换阶段冻结候选。
2. **失败后可恢复**：现有桥接分别替换 client.js 与 host.bundle.js，再 reconcile；失败处理保存 failed，没有看到完整的“保留上一已知可用版本、恢复整组产物、重新验证恢复成功”的流程。不能把 HMR 失败或发现漂移当成自动回滚。稳定控制器应能在需求插件损坏时工作，并为宿主故障保留外部恢复路径。
3. **业务验证独立且固定**：UI 内容存在、代码构建成功、单测通过均不保证业务需求达成。每条需求先固定可观察的业务 AC；变更后用真实 Desktop 操作验证排序、筛选、滚动、选择和恢复。实现侧不能降低本轮 AC 或把旧证据改称新证据。
4. **两层闭环分开**：同一需求内的开发/修复有界续推已有实现；跨需求持续发现问题、排序价值、隔离实施、独立验证、控制成本与提升基线的长期 loop 尚未证明完成。多 agent 只在独立验证或跨层定位有明确收益时使用，不以互评代替证据。

## 建议流程与成功判定

```text
稳定旧版录入需求并确认业务 AC
  → 固定代码与需求基线
  → DSH 执行器开发候选版本
  → 固定命令 + 实际业务操作验证
  → 运行空闲、安全交接
  → 稳定部署组件切换整组新版
  → 核对新实例身份与业务效果
  → 人接受效果；另行决定发布
  → 失败则恢复上一已知可用版本，保留证据
```

每轮只处理一个清楚目标，只有“旧版可复现问题 → 同一检查在新版通过 → 相关回归无新增失败 → 真实界面加载正确新版 → 人确认业务效果”的候选才计作有效改进。没有新增事实、预算耗尽或需业务决定时停止。

应优先将 REQ-ALM-001 做成首个完整、可重复的自举样本：固定原有排序/查询/滚动等业务要求，由 DSH 在插件内完成候选，验证真实 Desktop 效果和版本切换，留下一份 before/after 与失败恢复记录。人协助观察与业务验收仍属于合理的自我迭代；若 Codex 代写主要补丁，则应明确归因于外部协作。

价值以真实结果计量：完成一条验收需求的人工操作次数、重复“继续”的次数、返工、耗时、模型成本与新增回归。每轮改了多少代码、写了多少报告或增加几个 agent 不是有效改进指标。
