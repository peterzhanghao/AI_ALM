# 反馈与过程复盘 brief 的评估与任务化

- 评估对象：`docs/analysis/plugin-feedback-and-process-retrospective-brief.md`（2026-11-02，292 行）
- 评估基线：`develop` 分支，工作树含此前未提交改动（全部保留，未回退）
- 结论：**问题判断基本成立，产品切分顺序正确；但 20 条验收清单若一次做完会变成大工程，应严格按它自己给出的 N 节切片推进。本轮只落地切片 1（手动反馈闭环，零模型调用），切片 2/3/4 已转为带依赖的任务卡，不假装完成。**

---

## 1. 判断成立、本轮采纳的部分

### 1.1 两个入口必须分离（采纳）

brief 把「反馈与建议」和「自动过程复盘」拆成两个互补入口，而不是做成一个“AI 体验分析师”。这个拆法是对的：

- 手动反馈**不能依赖**自动观测可用：观测开关默认关闭时，用户仍然必须能说“这里很别扭”。
- 自动复盘**不能替代**手动表达：用户能直接说清诉求时，再让他回答一堆澄清问题就是浪费（上一轮意图澄清 v2 已经把“能零提问就零提问”写进协议）。

所以本轮先做手动入口，且把“自动复盘”做成设置里的一个**明确关闭的开关 + 说明**，而不是暗地里开始采集。

### 1.2 上下文必须“点击即冻结”（采纳）

现有 UI 是单页工作台（`client.js` 里 Workbench/需求详情/运行/意图弹层共用一套状态），面板一打开、页面一滚动、需求一保存，上下文就变了。如果反馈记录的是“提交时的当前页”，事后复盘无法还原用户当时看到的东西。

因此 `ContextEnvelope` 设计为**打开面板瞬间抓取、之后不可变**（`capturedAt`、`contextSnapshotId` 由服务端在保存时确定），并显式声明 `captureBoundary`（哪些信息被截断/未采集），而不是让模型事后“猜当时大概是什么”。

### 1.3 「发生位置 / 改进对象 / 需求归属」必须分离（采纳，且这是现有实现的真实缺口）

这是 brief 里最有价值、也最容易被忽略的一条。当前插件所有写操作都走 `rootFor(req)`（`packages/dsh-plugin-requirements/index.js:494`）——也就是**当前业务项目**：

- 用户在业务项目里用插件，发现插件本身有问题，点“生成需求”，如果按默认路径写，就会把“插件缺陷”写进业务项目的需求库；
- 反过来，插件开发者在自己仓库里调试，反馈的却是业务项目的需求质量问题。

这两种都会污染归属。因此本轮引入**独立的“插件改进需求接收工作区”设置**：反馈记录存在**观察 root**，生成需求写到**目标 root**，两者可以不同；未配置目标时反馈进入 `needs-routing` 待路由，**绝不静默退回当前业务项目**。

### 1.4 「代理空闲 / 等待输入」不能当作开发完成（采纳，有代码依据）

`index.js` 的 `startDeliveryRun` 在代理空闲回调里把运行标为 `waiting-input`；`delivery.mjs::deliveryStateFor` 把状态分成待推进/推进中/待验收/已验收/已关闭，其中 `accepted` 来自人工验收，`closed` 可能是取消、不做、重复。

这意味着：**不能**用“run 结束了”“测试红了又绿了”当成功证据。切片 1 不碰这条链路，但把它写进了不变量：反馈/复盘产物永远不能反向把运行标成成功；切片 2 的复盘里程碑也以“候选待验收 / 人工验收”为触发，而不是以 run 结束为触发。

### 1.5 允许零建议、允许“证据不足”（采纳）

brief 要求分析允许产出零条改进，证据不足时只保存观察。这与现有 evidence decision 的 `needs-clarification` / `blocked` 分级一致，本轮在提案模型里保留 `insufficient-evidence` 归因，并明确：**模型建议不能当缺陷证据**。

### 1.6 台账用 `.alm/` 文件、不建数据库（采纳）

现有 `failure.mjs` 已证明文件台账够用（`.alm/failures`、`.alm/defects` + 索引 + 指纹去重）。反馈沿用同一套形态（`.alm/feedback/records|proposals|settings.json`），不引入数据库或向量服务——brief 也没要求。

## 2. 需要修正的判断

### 2.1 「统一台账」不等于「同一个 schema」（修正）

brief §I 说复用失败台账。复用**机制**（目录、指纹、索引、状态机、脱敏）是对的；但反馈不是失败：

- 失败事件有 `failureKind`、重试、缺陷收敛语义；反馈大部分是体验建议，硬塞进 `failureKind` 会污染失败统计与 defect 看板；
- 因此本轮新增 `source='feedback'`（`asset.mjs` 的 `SOURCE_KINDS` 扩展一项），**真实缺陷类反馈**仍可后续走 `defect` 来源，但不做语义伪装。

### 2.2 「先保存后异步生成」在切片 1 里应更简单（修正）

brief §B 要求保存反馈后异步生成需求、回执对账。这个方向正确，但切片 1 若引入后台任务队列，就会提前背上切片 2 的复杂度（持久任务、补偿扫描、重启恢复）。

本轮的做法：**保存是本地同步写入 + 立即回执**（零模型，p95 应远低于 1s）；**生成需求是用户显式点击的同步动作**，失败保留 `needs-routing`/`failed` 并可重试。等切片 2 有持久任务机制后，再把“自动生成”接上去，避免现在造一个半成品队列。

### 2.3 验收清单 20 条要按切片拆（修正）

brief §O 的清单里，约 8 条属于切片 1（入口、不丢输入、关闭观测仍可反馈、归属路由、目标失败保留、双击幂等、回执、来源筛选），其余属于切片 2/3/4（里程碑触发、重复事件、迟到关闭、归因、效果回看、性能 p95）。

本轮只对切片 1 的条目负责；其余已在任务卡里写明验收条件，但**不宣称已完成**。

### 2.4 性能指标不能在本轮“实测”（修正）

brief §L 要求 p95 指标。当前真实宿主端口未监听（`61773` 无监听，Web GUI 有鉴权），本轮 UI 验证走离线 mock，只能验证“本地反馈是否立即出现”，不能给出真实宿主下的 p95。文档里会区分“已观察”与“未测”。

## 3. 明确不做（本轮）

| 不做 | 原因 |
|---|---|
| 自动过程复盘（事件采集、里程碑、模型分析、自动提案） | 属切片 2/3，依赖真实交付周期数据；先做会让手动入口被观测系统拖住（brief 自己也反对） |
| 效果回看 / ROI / 置信概率 | 需要样本量与对照设计；brief 明确禁止编造 ROI |
| 自动创建 run、改代码、发布、自动确认需求 | 越过现有授权边界；brief 也明确“生成需求 ≠ 批准开发” |
| 复盘自身失败时的递归分析 | 会形成自我优化循环，brief §K 要求禁止 |
| 新建数据库 / 向量检索 | 现有文件台账足够，brief 未要求 |
| 反馈面板做“十分钟访谈式”澄清 | 与上一轮意图澄清 v2 的“零提问优先”冲突；反馈应直接表达 |

## 5. 关键设计裁决

1. **观察 root 与目标 root 分离**：反馈写在用户当时所在的 workspace；需求写到设置里配置的接收 workspace；未配置 → `needs-routing`，不写业务项目。
2. **目标只能是可信工作区列表里的项**：`destination` 用 `workspaceId`/`projectId` 解析，服务端不接受任意路径，避免路径穿越与误写。
3. **零模型调用**：切片 1 的“生成需求”是确定性的 brief 组装（用户原话 + 上下文事实 + 未采集边界说明），不需要模型；也就没有“模型把反馈改写成漂亮需求”的失真风险。
4. **优先级必须显式选**：沿用现有 `create.mjs` 的 `priority` 校验（P0/P1/P2），但不默认、不猜；缺失返回 422。
5. **幂等**：`clientRequestId` 去重保存；重复 generate 返回同一需求，不重复建单、不重复触发。
6. **脱敏**：绝对路径、token/Bearer 形状在服务端脱敏；附件与材料内容只作为数据，其中的指令不改变授权。
7. **真实状态，不编造进度**：面板只显示服务端返回的状态与耗时；没有数据就不显示。

## 6. 与现有系统的关系

- **失败台账**（`failure.mjs`）：复用机制与目录风格，不合并 schema；真实缺陷可在后续版本以 `defect` 来源关联。
- **证据判定**（`evidence/decision.mjs`）：切片 1 不参与需求验收判定；切片 4 的效果回看以它为准，而不是“需求数量”。
- **需求创建**（`requirements/create.mjs`）：复用 `planRequirement`/`createRequirement`，反馈生成的需求是**普通待确认需求**，走既有确认与开发授权流程。
- **交付状态**（`requirements/delivery.mjs`）：切片 2 的复盘里程碑以 `deliveryStateFor` 与人工验收为准，不以 run 结束为准。

**已实现的行为（与 brief 切片 1 对照）**

1. **随时可用的入口**：工具栏“更多”→“反馈与建议”，任意页面可打开；抽屉不卸载工作台、不叠第二层弹层，Esc 关闭并回焦入口。
2. **点击即冻结上下文**：打开时抓取 page/stage/需求号/意图会话/运行等，面板顶部显示“已固定当前上下文 · 页面 · 需求号”；草稿在会话内保留。
3. **保存可靠**：`clientRequestId` 幂等；本地立即回执“已保存 FB-0001（Nms）”；失败显示错误原因并可重试且不丢内容；服务端补 `capturedAt`/observed 事实/`captureBoundary`。
4. **归属分离落地**：反馈记录写观察 root；生成需求写“改进接收工作区”（只能从可信工作区列表解析）；未配置 → 422 `destination-not-configured` 且反馈保持 `needs-routing`，**不退回业务项目**；不可写 → 422 `destination-not-writable` 且反馈保留可重试。
5. **真实待确认需求**：目标 root 出现 `source=feedback` 的普通待确认需求（brief 带“## 反馈来源”，不含绝对路径、不含 AI 结论）；重复 generate 返回同一需求；不触发 run、不改代码、不发布。
6. **优先级不猜**：generate 缺 priority → 422 `priority-required`；UI 强制选择 P0/P1/P2。
7. **收件箱与状态**：状态徽标（待路由/已路由/已转需求/失败）、计数、需求链接；类别可更新（追加 notes，不改 context）。
8. **设置面板**：接收工作区下拉、覆盖阶段/保留条数可存；自动复盘开关 disabled 并注明“后续版本”，`enabled` 本切片只读。
9. **来源筛选**：新增“反馈”，`全部` 包含反馈，缺陷/手动判定未回归。
10. **零模型调用**：整条链路不调用模型，因此不存在“模型改写反馈/伪造根因”的风险。

## 9. 已知限制

1. **UI 验证为离线 mock**（`tmp/ui-harness/server-feedback.mjs`）：真实宿主端口未监听/需鉴权，未做“真实 HTTP + 真实 UI”的浏览器联调；但服务端本身由 17 个真实 HTTP 用例覆盖。
2. **`intentSessionId` 依赖本次页面会话打开过意图弹层**：没有就不显示，如实省略，不推断。
3. **只读可写探测的边界**：`GET settings` 用 `probeWrite:false` 只读检查，无法发现 `.alm/feedback` 被普通文件占用这类写拒绝；`generate` 用真实写探测，能返回 422。
4. **并发写**：ID 分配为目录最大序号 + 写前存在性检查，单进程串行安全；多进程同时写同一工作区未加锁（契约未要求）。
5. **跨工作区联调**未在真实桌面宿主上跑过；插件测试用 `DSH_WORKSPACES_FILE` 指向临时 workspace store 验证。
