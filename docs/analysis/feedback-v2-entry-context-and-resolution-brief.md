# 反馈功能第二轮评审：入口一致、现场可信、提交后有处理闭环

日期：2026-11-03。性质：源码静态审查、界面评审与 DSH 开发指令；本次没有实施功能或进行真实宿主交互测试。

## 1. 结论与证据边界

当前反馈已具备“保存记录、配置接收工作区、显式转需求”的基础，但仍偏向一个独立录入表单。需要升级为全流程可达、上下文正确、提交后可继续处理且能跟踪结果的产品能力。

用户反馈“需求详情没有反馈按钮”是当前实际使用问题。当前源码的 DrawerContent 已有 data-drawer-feedback，ModalShell 与工具栏也已有入口。因此不能直接断言源码没写，也不能拿源码存在否定用户体验。需要检查运行中的插件身份、客户端 bundle、是否命中该组件、响应式遮挡、渲染异常、是否有其他详情实现等，验证真实可见且可点击。

本次依据用户截图，以及当前 `client.js`、插件 `feedback.mjs`、`alm-core/src/feedback/*` 和既有实施评估。旧评估中部分 UI 验证使用离线 mock，不是本次真实宿主验收依据。本文件中的代码问题为静态观察或风险判断，涉及实际运行结果的部分需实施时复现。

## 2. 当前功能的关键问题

### 2.1 入口不是系统能力，依赖各页面手工加入

现有全局 FEEDBACK_LAUNCHER 由工作台在渲染时赋值，弹层通过 launchFeedbackFromLayer 转调，未就绪时静默返回。入口存在与否、上下文是否准确，依赖具体页面有没有正确接入。只给几个公共壳加按钮仍可能遗漏自定义详情、错误页、快照页和独立入口。

这是覆盖与运行验证问题，应建立页面/弹层清单和自动检查，不能再采用“想到一个页面加一个按钮”的修补方式。

### 2.2 表单把“报告问题”和“管理需求”混在一起

截图要求用户理解类别、上下文勾选和 P0/P1/P2，再在“保存反馈/生成需求”之间选择。类别待判断合理，优先级却过早：反馈者不应先承担需求分诊与排期责任。

两个按钮没有解释后续路径：保存后是否有人或 AI 处理？生成的是原话记录还是可开发需求？生成后是否进入正式排期？这些应通过统一提交和明确回执回答。

当前 footer 在收件箱页也渲染保存/生成按钮，仍操作后台 compose 状态。用户查看历史时不应误提交另一份草稿。

### 2.3 “上下文已固定”目前强于实际保存能力

- freezeFeedbackContext 主要从 selected 读取需求/run，ModalShell 只传标题。弹窗可能对应与 selected 不同的需求，页面标题与实际关联对象可能分离。
- 意图引用来自全局 LAST_INTENT_SESSION_ID，可能是上一次不相关会话。不能把“最近看过”当“当前关联”。
- frozenAt 在前端生成，但 buildContext 未带回；服务端 capturedAt 使用保存时间。点击发生时刻与服务器接收时刻混淆。
- 前端将 recentError 放入 ui.recentError，服务端 UI_KEYS 不包含此项，后续 normalizeUi 也无此字段，可能在落盘前被丢弃。界面勾选“最近错误”不等于错误正文已保存。
- 当前需求只记录业务 ID，未携带修订和稳定实例键，无法充分证明是用户看到的哪条记录、哪个版本。
- 关闭草稿后重开会重新抓上下文，但 FEEDBACK_DRAFT 沿用原文本/保存 ID；同一草稿的文字与现场可能被拼错。

因此要检验从“屏幕显示 → 请求 → 持久化 → 后续分析”的完整保真链路，不能只检查复选框。

### 2.4 保存不等于处理，生成不等于需求就绪

当前 generate 是零模型调用：以首个非空行生成标题，把原话和上下文拼成 brief，然后创建需求。这适合作为候选记录，不足以声称已完成根因分析、澄清和可开发规格。

当前收件箱展示状态、摘要和已生成需求链接，但缺少打开反馈详情、补充、更改路由、从已保存反馈继续生成、分诊、关联已有问题、暂缓/不采纳和结果验证等完整动作。已保存但未转需求的记录容易停在收件箱。

### 2.5 跨工作区与幂等还有断点

- 服务端支持在目标工作区创建需求，但 UI 查看需求回调只传 ID 并调用当前工作区的 openRequirementById；目标工作区信息在导航中丢失，可能打开错记录或找不到。
- 生成幂等主要依靠进程内锁和反馈已转需求状态。需求写入成功、反馈关联更新失败时，再试存在重复创建风险；跨进程/重启不能靠内存锁解决。
- 反馈 save 的幂等按 clientRequestId 查旧记录，未比较内容摘要。同键不同负载可能返回旧内容而让用户误以为新内容已保存。
- 转化前没有把跨反馈提案去重作为创建需求的硬前置。事后保存 proposal 不能保证同一问题只创建一条需求。
- 修改已保存反馈内容/类别/勾选会 clearReceipt，下一次 save 可能创建另一条记录，应明确“补充原反馈”与“新建反馈”。

### 2.6 多层覆盖与焦点语义不一致

截图是列表、需求详情/决策弹窗、反馈抽屉同时存在，多个遮罩叠加。FeedbackDrawer 虽有遮罩阻挡背景，却标 aria-modal=false，且主要处理 Escape 和初始聚焦，缺少完整一致的顶层焦点约束；returnFocus 取菜单按钮而不总是真正触发元素。

打开反馈应保留原任务，但不能让用户面对多层交互竞争，也不能让键盘穿到被遮挡的执行按钮。

## 3. 推荐交互

### 3.1 全流程一个标准入口

工具栏与所有核心页面/弹层标题工具区都提供低强调、可读的“反馈”文字按钮。需求详情即使滚动、窄窗或打开运行问题，入口仍可达。界面容器统一接入反馈服务，业务页面负责提供自己的上下文对象。

键盘入口可作为补充，但要检查宿主快捷键冲突；不能把它作为缺少按钮的替代。不默认增加漂浮气泡遮挡正文。

### 3.2 写反馈只保留一个必填项

```text
反馈与建议                                      关闭

哪里出了问题，或希望怎样改变？
[输入描述；允许粘贴或添加截图]

发生位置：需求详情 › 交付 › 回答决策请求
已附带当前需求、当前运行、错误摘要       查看/调整
改进对象：需求插件
需求接收：插件开发工作区                 更改

▸ 更多信息（可选：期望结果、类别等）

保存后整理为待确认的改进需求；不会自动开发。
                                      [提交反馈]
```

选择“提交反馈”即授权保存并整理该条反馈；不能因此启动开发、恢复原 run 或执行发布。提交后先返回可靠保存回执，分析在后台进行，用户可以立即返回原任务。

不在写反馈阶段要求优先级。若当前正式需求格式强制优先级，可先生成独立候选，准备正式写入时由维护者集中选择；不得偷偷默认 P1/P2，也不能因缺优先级拒绝保存。

截图是可选证据，默认不录屏。收件箱作为单独的管理视图或可返回页面；切到收件箱时 footer 改为相应处理动作，不保留 compose 提交按钮。

## 4. 反馈提交后应该如何处理

系统负责保存、核对、去重、整理与追踪；维护者负责确认范围、优先级及执行决定。单人使用时维护者就是当前用户，不引入虚假的“已分派给团队”。

| 步骤 | 系统行为 | 用户看到什么 | 需要人做什么 |
| --- | --- | --- | --- |
| 可靠保存 | 保存原话、现场与提交回执 | 反馈 FB-xxx 已保存，可返回原任务 | 无 |
| 核对与分诊 | 校验关联、检查已有问题与证据，判断改进对象 | 整理中或等待配置 | 必要时选择接收工作区 |
| 整理候选 | 提出问题、期望、范围、候选验收及未决项 | 待确认候选；事实与假设分开 | 只补关键缺口 |
| 关联/转需求 | 已有问题则关联；新问题写真实待确认需求 | 关联已有需求或已生成待确认需求 | 写入必要字段缺失时集中处理 |
| 确认并推进 | 复用现有需求评审与开发流程 | 待确认、排期/推进情况 | 确认范围与开发授权 |
| 修复与验证 | 回写实际候选、测试和验收结果 | 待验证、已验证或仍有问题 | 必要时确认原问题已解决 |
| 结束与回看 | 保存处置理由与效果证据 | 已解决/不采纳/重复等明确结果 | 可重新打开或补充 |

分类结果也必须有出口：

- 明确的新缺陷/体验改进：生成待确认需求；用户选“缺陷”本身不是已证实根因。
- 重复：关联已有问题，追加独立证据；说明为什么判重复，可纠正。
- 使用疑问：基于真实资料回答，用户确认或维护者标记已答复，不为了数量造需求。
- 证据不足：保存待补充/待调查，仅问影响处理的一两个关键问题；“没有证据”不是“问题不存在”。
- 不采纳/暂缓：写明确理由和适用范围，原话与记录保留，可重新审视。
- 外部依赖/业务代码问题：保留正确归因；若插件容错或提示存在独立改进机会，再生成对应插件需求。

“已生成需求”不是反馈处理终点；测试通过不是“用户体验已改善”的充分证据。涉及原问题复现与体验的，需要相应复核；无法验证时明确“待验证”，不能自动关闭。

## 5. 可直接交给 DSH 的开发重构指令

以下为真实插件开发任务，请先检查适用仓库约定和当前实现，保护所有无关未提交修改。复用现有反馈台账、需求澄清、失败监控、目标工作区设置和执行器。不要只补几个按钮或交静态样机。

### A. 先解决运行中入口缺失

1. 列出实际入口：需求列表、详情全部页签、创建/意图澄清、评审、开发前检查、运行/日志、回答决策、测试/验收、缺陷详情、版本/差异、错误态及反馈收件箱。
2. 核对实际宿主加载的插件实例、源码路径、服务端版本、客户端 bundle 构建标识；通过宿主支持的诊断入口验证，不扫描或输出凭据。
3. 解释源码已有详情按钮但运行中不可见的原因。包括旧 bundle、重构覆盖、自定义容器漏接、布局遮挡等都只是待查候选，未经验证不得断言。
4. 建立统一 FeedbackProvider/launcher 和容器工具区。名称与实现沿用现有 React 模块方式，不要求引入框架。页面注册结构化上下文，不用模块级最后赋值函数作为唯一业务路由。
5. 服务暂不可用时显示可操作错误和本地待保存状态，不允许点击静默无响应。嵌入、独立页若不支持写反馈，应明确范围并给真实可用入口。
6. 核心页面的反馈必须真实可见、可点、键盘可达，而不是 DOM 中存在隐藏节点。为新增页面建立覆盖检查，减少后续重构再次漏掉。

### B. 上下文以当前交互对象为准

由详情、run、意图或弹窗组件明确提供自己的：工作区、需求实例与修订、当前页签、run/决策/候选、实际错误与必要输入摘要。顶层 selected 和最后一次打开的意图只能作为经验证的后备。

记录 `observedAt`（点击冻结的客户端观察时间）、`receivedAt`（服务端接收）、持久化快照 ID 与来源。观察时间可验证格式但不能冒充服务器可信时钟，保留时区/时间来源；如未采集则明确缺失。

打开时冻结现场，在保存阶段做 schema 校验、脱敏和落盘；后续服务端补取引用内容要标其读取时间与版本，不能声称全部是点击时状态。

当前对象标识至少包含工作区、稳定实例/文件身份、业务 ID 和修订；同业务 ID 记录不混淆。请求目标 root 绑定冻结工作区，不能提交时用已切换的全局 data.root。

补齐上下文白名单到持久层的映射：最近错误放入受支持的 runtime/evidence 字段；原始错误、错误码、观察来源可以分别记录。测试必须读取落盘文件核对正文，不能只看前端勾选或回执 ID。

需要时保存当前问题摘要、决策 ID、run 状态、需求内容 hash 与脱敏的未提交内容片段；记录数据缺失、截断和未覆盖范围。用户原始业务回答不是修复授权，反馈内容也不得送入原 run 的回答接口。

取消某项上下文时，移除正文、引用及可反推出它的隐藏字段；不要只取消界面勾选。保留必要的最小路由信息与删除范围说明。已知 ID 并不自动表示用户授权读取整个项目历史。

附件可粘贴/选择，保存内容、类型、hash、引用与读取能力；没有截图能力时不显示“截图已保存”。可选截图不成为提交前置。

### C. 草稿、补充和幂等

1. 草稿按工作区与捕获实例隔离；关闭再开允许“继续原反馈”或“新反馈”，继续时保留原现场。不能旧文本自动搭配新上下文。
2. 保留未提交草稿的方式按现有数据策略实现，不能默默上传或写入明文浏览器通用存储；刷新恢复范围明确可见。
3. 已提交反馈的补充采用同一 ID 加修订/追加说明，不因改类别或勾选自动变成新记录。已保存原话与快照不可悄悄改写。
4. 同幂等键同负载返回原回执；同键不同负载返回冲突并保留新输入，不伪称已保存。
5. 背景保存失败、响应丢失或关闭面板不丢输入；不以面板卸载作为任务取消或成功判据。

### D. 简化表单和覆盖层

采用本文件第 3 节的单主动作表单。类别、期望、附件可选；优先级移到管理/正式转化步骤。目标产品与接收工作区在提交前用一行说明，避免失败后用户才知道需要配置。

收件箱和写反馈的动作独立；保存中/整理中/已转需求的回执分别清楚显示。正式转需求尚未发生时不能用绿色“已完成”。

反馈表单保持非破坏性，关闭后回到准确的原弹层/页签/输入与焦点。使用统一的最上层管理：若遮罩使背景不可交互，就实现真实模态语义、inert/焦点约束、唯一 Escape 所属；若非模态则不假装模态阻断背景。

不叠加多层重模糊，不让原决策弹窗响应反馈面板的键盘事件。反馈关闭不会关闭原需求，不取消 run，不提交原业务回答。

不在每个组件复制一套相同样式；复用标题工具区及反馈面板。深浅色、窄屏、200% 缩放都可提交；footer 在视口可达。

### E. 提交后的整理能力

保存必须零模型依赖并立即回执；正常本地环境目标持久化确认 p95 ≤1s，实际测量并报告。模型不可用不能阻止保存。

提交按钮明确表示后续会整理为候选。保存成功后建立持久、可恢复的处理任务；复用既有任务机制，若没有则只实现本需求必要的小型任务记录、串行处理和启动恢复，不要求通用编排平台。

处理顺序：

1. 核对上下文有效性、目标产品和路由。
2. 检索权限范围内的反馈、缺陷及已有需求，给保守重复判断。
3. 证据足够时直接生成紧凑候选；需要语义分析时使用现有模型，一次有界分析，最多一次格式修复。
4. 明确区分用户陈述、代码/运行事实、原因假设、待验证方案；不把原话变成已经独立观察的事实。
5. 候选包含问题、期望、范围、建议行为、可测试验收、证据与未决项。任何 AI 新增行为都标为建议，未经确认不作为承诺。
6. 不要求每条反馈自动读整仓、跑测试或执行复现命令。需要深入调查时生成明确的只读调查任务，写明读取边界。

模型失败显示“反馈已保存，整理失败，可重试/人工处理”。用户可直接按原话建未就绪候选，不因模型故障被困住。

若首次交付只支持确定性原话候选，必须标“原话候选，尚未分析”，并实现后续整理入口。不能将首行截断 + brief 拼接描述为已完成需求澄清。

### F. 状态用事实拆分，界面用人话呈现

不要把路由、分析和修复都塞入单个 status。建议在兼容现有记录的基础上分离：

```text
capture: saved / save-failed
routing: configured / needs-routing / unavailable
processing: queued / analyzing / needs-info / draft-ready / failed
disposition: undecided / linked / converted / deferred / declined / answered
resolution: derived-from-linked-work / awaiting-verification / verified
```

这是一种逻辑契约，字段名按现有模型调整。UI 投影为少量明确阶段：“已提交、整理中、待补充、待确认、已关联/已转需求、推进中、待验证、已解决、暂缓/不采纳”。显示下一步原因，而非仅显示“已路由”。

需求推进状态从真实关联对象读取，反馈记录不要维护第二套会漂移的开发状态机。读取目标工作区失败时显示未知/暂不可读，不把它映射成未开发或已解决。

保存回执带反馈稳定引用、保存时间、当前处理状态、下一步与查看入口。无人负责或尚未分析时，不显示“团队处理中”。

### G. 收件箱升级为处理台

每条反馈可打开详情，查看原话、现场、分析/候选、处置和关联进度。必须支持从历史记录继续处理，不依赖当前 compose 表单。

提供按当前状态、类别、来源页面和关联需求筛选；列表项显示一句摘要、明确状态、时间和一个当前动作。默认当前工作区范围可见，跨工作区聚合需有授权与来源标记，不能假装全局收件箱。

动作包括：补充反馈、配置/更改目标、重新整理、确认候选、选择优先级、转需求、关联已有需求、标重复、暂缓、不采纳、标记误判、验证解决。仅显示真实支持且当前状态允许的动作。

用户在同一应用中作为维护者处理即可，不为单人场景强制建复杂分派系统。已有角色模型存在时复用权限；没有则如实显示操作者。

不采纳/暂缓/重复需理由与关联，可重新打开；反馈不是删除后消失。暂缓建议不因重复扫描持续弹窗催办。

### H. 跨工作区转化与去重

显示发生位置和需求归属。插件建议默认使用已配置的插件开发接收工作区；无配置继续保存/整理，停在待路由，绝不回写业务项目。

查看关联需求传完整引用 `{workspaceId/projectId, stableRequirementRef, id, revision}`；服务端从可信映射解析根路径。不能只把 ID 交给当前工作区查找。切换工作区前保存/保留原任务，返回路径可恢复。

创建前先处理重复建议。结构化指纹覆盖目标产品/组件、问题与期望，跨反馈实例去重；别仅依赖相同文本，也别让模型说重复就覆盖用户记录。保留所有独立反馈与合并理由。

引入持久 conversionId/sourceFeedbackRef，在目标需求/回执中记录稳定转化标识。需求创建后关联保存失败，重试先按转化标识对账，发现已有需求即补链，不能再创建。

考虑多窗口、多进程、重启与两工作区写入无法原子提交的情况；内存锁只是优化，不能作为唯一一致性保证。跨工作区用幂等落盘与对账形成最终一致，错误状态如实表达“需求已创建，关联待恢复”。

反馈来源与性质分别记录。用户选缺陷是报告分类；经确认的插件缺陷可连接现有缺陷台账，但不自动创建第二条相同需求。

### I. 真正的待确认与开发边界

现有 generate 创建 source=feedback 的需求，不足以证明它会受“待确认”约束。必须核对列表、下一步与直接启动 API：

- 原话候选/未确认提案可保存、查看、编辑。
- 未确认范围或存在开发阻塞项时，不得自动成为可执行任务。
- 确认候选与优先级后，复用现有需求评审及授权流程。
- 不创建自动 run，不把反馈发给业务 run 当“回答并继续”，不自动改插件代码或发布。

若使用独立提案台账表达待确认，需求视图和启动检查必须读取其真实状态；不能仅贴一个“待确认”标签而后端仍能直接启动。

此处约束自动转化的候选，已有明确授权的修复开发仍按现有业务规则推进，不能因此增加重复审批。

### J. 解决反馈与回看效果

把需求、候选、测试和人工验收的真实结果投影回反馈详情。测试通过后按问题性质判断是否还需复现/体验确认：按钮缺失需要验证按钮真实可见可点；等待慢需要对应时延测量。

结果显示修复版本、相关需求、验证方式、尚存限制；反馈者可选“已解决”或“仍有问题”。仍有问题优先追加原反馈或标疑似回归，不自动另建十条需求。

只在有新状态或需要决定时轻量提示，默认不外发消息、不创建额外定时自动化。无人响应不自动当解决；关闭需求也可能是重复或不做，应映射相应处置。

### K. 用截图场景作为回归案例

截图中，业务 run 为 waiting-input，回答弹窗提示“没有找到决策请求文件”，反馈面板顶部又展示需求详情/测试。需要实际核验并处理两个独立问题：

1. 反馈必须记录真实来源“回答决策请求弹窗”，关联正确 run、需求、缺失决策事实与观察时间，不被历史缺陷阶段覆盖。
2. 原业务的“缺失决策文件”不应默认转成用户必须随意写一句授权来恢复；明确是暂时读取失败、确实无决策请求还是正常人工交接，按实际情况恢复或显示对应动作。若与本轮反馈重构无关则生成关联问题并写明尚未修复，不能宣称已解决。

提交反馈后，原回答表单的输入、run 等待状态和授权边界保持；关闭反馈只关闭反馈层。反馈过程发现异常可以记录，不能递归触发无限自我反馈。

### L. 实施与验收

按以下顺序交付可用切片：

1. 真实入口覆盖、运行版本核验、上下文保真和草稿隔离。
2. 单主动作提交、可靠保存、收件箱详情及历史继续处理。
3. 后台整理/候选、确认与跨工作区幂等转化。
4. 关联推进状态、解决验证、故障恢复与可访问性。

每个切片标实际覆盖范围。不要再次只完成保存和拼接需求，却把“反馈闭环”写为全部完成。

最低验收：

1. 真实宿主需求详情、全部页签及核心弹层都能找到并打开反馈；服务端与客户端构建身份可核对。
2. 弹层对象与底层 selected 不同时，捕获弹层真实对象；历史意图不会串入。
3. 打开后切工作区/需求，再提交仍保留原现场归属。
4. 错误正文、决策引用、修订、观察/接收时间从 UI 到落盘、分析、候选都可核验；取消勾选后无隐藏残留。
5. 原草稿恢复不套用新现场；修改已保存反馈为补充修订，不悄悄重复提单。
6. 保存不依赖模型和优先级；保存后回执真实，模型失败可从收件箱恢复。
7. 旧反馈在收件箱中可配置目标、补充、整理、转需求，不依赖隐藏 compose 状态。
8. 跨工作区同 ID 查看正确目标；无配置不污染业务项目。
9. 转化中途崩溃、关联失败、重复点击、多窗口和响应丢失均不重复创建需求。
10. 同幂等键不同内容明确冲突，不返回伪成功。
11. 用户陈述不当作已核验缺陷，生成候选不伪装成可开发规格；来源指令不改变权限。
12. 重复、答疑、证据不足、暂缓和不采纳均有真实处理出口。
13. 自动整理与创建待确认需求不启动开发；反馈内容不会成为业务 run 的回答。
14. 需求关闭/测试通过不会自动等同反馈解决；按钮/延迟等按原问题验证。
15. 顶层焦点、Escape、遮罩、回到原任务、窄屏及 200% 缩放验证；收件箱不显示错误提交动作。
16. 当前截图所示“缺失决策请求”场景可反馈、可追溯且不会误恢复业务运行。

进行核心逻辑和 UI 测试，并验证真实插件入口、保存落盘、跨工作区导航与创建回执。mock 可覆盖故障路径，不能替代真实可见性或模型质量验收。

最终提供：入口覆盖矩阵、版本/运行问题结论、上下文数据流与状态表、修改文件、反馈到处理到验证的演示和测试证据，以及尚未支持的能力。没有实测的性能、真实用户研究和宿主行为明确标为未验证。
