# 需求描述 v5：把澄清结果沉淀为可执行的需求正文

日期：2026-11-04。用途：交给 DSH Harness / Codex 的专项重构指令。

本版补齐 [v4](requirement-detail-v4-first-principles-brief.md) 的内容链路，不推翻完整页面、授权内推进与独立人工验收规则。本文件是分析与待实施任务书，未修改真实需求或产品代码。

## 1. 结论：需要生成正式描述，但不能只是扩写原话

**需要 AI 将原始意图、有效澄清回答、人工修改及已核实上下文整理成详细需求描述。** 该描述先作为可编辑草稿呈现，经现有需求确认动作形成正式版本，再进入详情，成为执行和验收共同使用的内容。

应补齐的链路为：

```text
原始意图 + 有效澄清回答 + 人工修改 + 已核实上下文
  → AI 整理结构化需求草稿
  → 用户查看/编辑，在已有确认步骤中确认这一版本
  → 持久化正式需求正文与来源绑定
  → 详情完整展示相同版本
  → 执行器读取本轮绑定的正式版本
  → 验收逐项对应该版本的 AC
```

“详细”指开发者可以理解行为与边界、用户可以判断是否符合意图、测试者可以验证结果，不规定字数，不强制每条小需求生成长 PRD。原文已充分时可以直接整理，不需要为了生成描述再增加一轮澄清、模型调用或审批。

需求草稿确认、授权开发、交付候选验收是不同动作。这里的“需求草稿”不是运行完成后用于签收的 CAND，生成描述不能自动开工、签收或发布。

## 3. 直接执行的重构指令

请围绕“澄清结果成为正式需求正文”完成实现，保留所有既有未提交修改。先核对当前版本和仓库约定，不重置工作区，不覆盖真实需求与旧证据。

### A. 一份结构化正文，多个界面共用

复用现有意图 candidate、需求 BRIEF、版本与来源机制，补齐所缺字段和共享渲染能力。不要另造一份只有详情页能看到、执行器不读取的 AI 文案。

优先方案：在现有 candidate 中增加必要的详细行为条目，形成可版本化的需求文档契约；由共享转换函数无损生成规范 BRIEF。确认、预览、详情和执行从同一正式内容版本读取。若采用结构化正文作为持久化主源，则 Markdown 是派生视图；两者不能分别可编辑而没有一致性规则。实施说明须明确主源、编辑入口与版本绑定方式。

最小内容结构：

| 部分 | 应回答的问题 | 约束 |
| --- | --- | --- |
| 问题与目标 | 谁在什么场景遇到什么问题，希望得到什么结果？ | 分开表述，不把整段原话复制两次 |
| 详细功能行为 | 用户做什么、系统如何响应、关键状态和例外是什么？ | 按实际功能拆成稳定条目，如 FR-01；不是只有一句范围口号 |
| 本次范围与不包含事项 | 本轮承诺做哪些，明确排除哪些？ | 未确认的排除不能由 AI 自行补成承诺 |
| 验收要求 | 什么条件下做什么，应看到什么，如何判断？ | 稳定 AC ID，关联功能条目；保留既有 AC ID 与含义 |
| 必要约束 | 有哪些明确的兼容、数据、权限或体验限制？ | 只写已有约束，不凭空生成性能指标、平台和技术方案 |
| 待确认与建议 | 哪些尚不确定、哪些仅为 AI 提议？ | 与正式条款分开；真正阻塞仍沿用既有澄清规则 |
| 来源与版本 | 哪次输入、回答、人工修改形成这一条款？ | 来源可追溯，原话/附件不替代正文 |

详细功能条目至少能表达：稳定 ID、名称、行为描述、必要的前置/操作/响应、实际相关的异常或边界、来源引用。小需求允许一个条目；不强制没有意义的空字段，不为每条功能编造完整状态机。

标题、一句话目标、范围清单和 AC 不能完全替代详细功能行为；功能描述解释“系统应该怎样工作”，AC 解释“如何判断满足”。两者关联，避免手工维护重复且矛盾的正文。

### B. 在现有澄清过程中形成草稿，确认前可见

每轮分析后，基于当前输入修订、未被替代的回答、人工锁定字段及已核实上下文更新草稿。已经回答的决定必须进入相应行为/范围/AC，而不只是藏在回答历史中。因新事实修改旧决定时保留变化说明。

优先扩展现有分析输出，不新增固定必经的“再写一份 PRD”模型阶段。最终整理若确有必要，沿用当前会话与因果版本约束，保证生成失败可重试，不重新追问已答事项，不重置澄清预算。

澄清区提供“需求草稿”预览：目标、详细行为、边界、AC 均可查看和编辑；轮次更新给出有意义的内容变化，不仅显示“分析完成”。用户不应先创建需求，才第一次看到 AI 整理的承诺。

草稿来源至少区分：用户明确陈述/回答、人工编辑、已核实项目事实、AI 推导或建议。AI 可以归纳和组织事实；新增业务规则、量化阈值、范围排除或权限承诺必须标为待确认。用户未选择、未反对或模型推荐都不等于采纳。

确认沿用现有一次确认操作，绑定用户实际预览的有效草稿。不要再增加一次等价强制评审。无新增承诺的格式整理不需要重复人类确认；确认后的语义变更必须走版本更新。

### C. 确认保存用户看到的这一版本

服务端重新计算并核对草稿内容 hash、inputRevision、当前草稿修订与上下文绑定；不能直接信任客户端传来的 contentHash。所有影响正文的人工编辑、回答和再分析都应使旧预览失效，用户确认旧版本时返回明确冲突并保留输入。

在提交的幂等事务/日志中保存：正式需求内容、条款 ID、来源与确认快照关联，以及现有确认回执。重试恢复相同计划，不再次生成不同描述、不创建重复需求。多条意图分别形成对应正文，回答不能串到其他条目；change/reuse/investigate/answer 路线仍保持各自语义，不为所有路线创建新需求。

Markdown 输出使用统一规范章节，例如 `## 详细功能`、`## 本次范围`、`## 不包含事项`、`## 验收要求`。移除“整份候选内容塞进背景，再重复目标”的包装方式。前后端共享正文契约或规范解析器，不能继续各自维护不同的标题白名单和正则。

既有加粗标签、老 BRIEF 与人工 Markdown 应兼容读取。读取不自动改写正式内容；解析不支持时显示完整原文并提示，不静默把正式范围或 AC 收进背景。

移除正文接口的静默 8000 字符截断。列表可以返回明确标注的摘要；详情与执行必须读取完整正文。若因大小限制需分段或按需加载，返回总长度/完整性标记与版本，所有条款可达；不能让截断文本被保存回去覆盖原文。超出支持上限应明确拒绝或提示，不无声丢失尾部限制。

### D. 详情默认展示正式需求描述

保留当前完整页面，在当前事项之后增加清楚的“需求描述”主区：

```text
需求标题
当前真实事项 / 必要决定

需求描述                                      编辑
〈一句目标〉
〈问题与场景；与目标不同且确有内容时展示〉

详细功能
FR-01 〈真实功能名称〉
〈操作、系统响应和关键边界〉
FR-02 …

本次范围 / 不包含事项 / 必要约束       有内容才显示

验收要求
AC-01 …                               对应 FR-01
AC-02 …

待确认事项 / AI 建议                    若存在，明确未纳入
原始意图与澄清记录                      按需展开
来源、修订与确认信息                    按需展开

交付验证
〈对上述 AC 的本轮结果与证据〉
```

正文中的“验收要求”与下方“交付验证”职责分开：前者是约定，后者引用同一 AC ID 展示结果，不复制维护第二份可编辑验收文本。

正式描述默认可读，不能全收进“原始诉求与背景”或“技术信息”。长文可提供段落锚点与适当折叠，但关键范围/限制不能被摘要截掉；不引入新页签和套层弹窗。渲染 Markdown 做安全处理，不执行原始 HTML、脚本或附件指令。

显示准确来源状态：“AI 整理 · 未确认”“已确认需求描述”“根据现有正文展示”等，具体措辞按真实记录确定。不要只因文本由模型生成就永远标成可选建议；也不能因为写进文件就标为已确认。

### E. 正式描述进入执行和验收

执行器启动时读取已确认/已授权的正式需求版本及完整 AC；不能仅传标题、原始意图摘要或截断 brief。运行记录绑定本轮需求版本与内容 hash，执行中查看详情能区分“本轮执行约定”和“最新编辑草稿”。

正文语义、范围或 AC 改变时，按现有候选/证据绑定规则判断失效；新版本未经授权不得静默用于旧运行。来源展示、字体或 Markdown 规范化等变化是否影响内容 hash，必须沿用明确一致的契约，不能借格式整理把旧签收或授权移植到不同内容。

每个已确认功能均应有相应 AC，或明确说明只能人工验证/暂未形成判定条件；不能用“运行过通用测试”替代业务覆盖。复用现有 readiness 对真正阻塞缺口的判断，不为了文档模板完整新增“每节必填”的门禁。

### F. 历史需求补全走显式草稿，不后台重写

对 REQ-ALM-001 这类历史正文，先核实来源回执、人工采纳记录、后续决策、实际已有 AC 和当前运行。能确定的已正式条款保留；来源不充分时如实说明。

详情提供按需“整理需求描述”入口，利用当前正文与可验证关联材料生成补全草稿，展示与现有正文的差异、来源和未确定项，用户明确保存后形成新版本。没有关联的澄清会话不能靠标题相似强行拼接。

对“AI 评审建议（已采纳）”要保留真实采纳事实，核对究竟哪些建议成为当前约定；不能简单归入“全部未确认”，也不能照单全收成新的正式范围。若证据冲突，呈现冲突并请求最小必要决定。

不从当前实现倒推出需求承诺，不从测试文件或通过结果反向改写 AC，不凭“苹果级体验”等形容词生成已确认的查询条件数量、排序同值规则、表头吸顶或性能阈值。已有证据能够支持时才引用。

不批量覆盖历史需求，不自动重新签收/发布，不打断真实运行。受运行写入约束时可保存独立草稿，按既有规则明确何时允许应用。

## 4. 最小示例：本条需求怎样整理才合理

下列仅为基于当前原话的待确认结构示例，不是已完成澄清后的正式内容，不写入真实 REQ：

- **目标**：让新建需求更容易被发现，并能浏览超出当前可见区域的列表内容。
- **FR-01 新建需求的默认位置**：需求列表默认按创建时间降序展示，使较新需求排在较前位置。
- **FR-02 浏览较长列表**：当列表内容超过可视区域时，用户可以纵向滚动，访问后续需求。
- **待核实**：同时间排序规则、创建后是否立即刷新并定位、滚动区域/表头行为，以及查询优化的具体范围；先查已有正式决定，不能默认再次追问，也不能自行补成承诺。

“查询条件优化”和“苹果产品级体验”需要由已有澄清结果/真实采纳记录转成可观察行为，单纯保留形容词不足以指导开发。示例没有覆盖全部原始诉求和已采纳内容，不能替代实际整理结果或删除原有范围。

## 5. 实施落点与最小验收

| 落点 | 修改目标 |
| --- | --- |
| `intent/messages.mjs`、`analysis.mjs`、`session.mjs`、`view.mjs` | 详细行为与来源契约、归一化、人工编辑保留、按输入修订更新、完整预览 |
| 插件 `intent.mjs` 与 `client.js` 意图编辑/确认区 | 字段透传、差异预览、确认绑定、延迟响应和并发冲突处理 |
| `intent/confirm.mjs`、`requirements/create.mjs` | 共享正文生成、确认快照、幂等落盘、避免背景/目标重复 |
| `query.mjs`、`detail-view.mjs`、详情组件 | 完整正文读取、统一解析、来源与正式条款区分、历史兼容 |
| 执行提示、运行版本与验收关联 | 读取相同正文版本、FR/AC 对应、修改后的证据失效 |

源码持续变化，以上为模块落点，不把行号当成固定实施位置。按 v4 约定构建真实宿主入口并核对加载版本，不手改 bundle，不为验证打断真实运行。

必须完成以下验证，新增测试聚焦数据丢失、版本竞争和实际行为：

1. **真实澄清→确认→详情→执行闭环**：隔离新建需求，至少一次重大澄清回答；回答内容进入相应条款，确认前预览、落盘、详情、执行输入语义一致；真实模型证据与固定契约测试分别标识。
2. **零澄清与生成失败**：信息充分无需为了写描述多问一次；模型失败可保留输入/人工补稿，不重复创建或返回伪完整描述。
3. **来源与承诺边界**：AI 新建议未采纳时不进入正式承诺；实际明确采纳的条款不会因归类为 AI 而被隐藏；冲突和未知不伪装已解决。
4. **版本与并发**：人工编辑不被迟到生成覆盖；旧预览确认被拒；重试只产生同一需求与相同正文；多意图不串内容。
5. **格式兼容**：规范章节、旧加粗标签、嵌套清单、人工 Markdown 与未知标题不丢条款；背景、目标不整段重复。
6. **长文完整性**：超过 8000 字符，末尾含关键排除/AC 的正文，在详情、执行及编辑保存后仍完整存在；验证不是仅显示“更多”入口。
7. **历史补全**：对隔离副本验证差异预览和明确应用，不直接改真实 REQ-ALM-001；没有可验证会话关联时不得编造澄清来源。
8. **证据与 UI**：正文可读且主要限制可达，AC 与验证结果对应；内容变化后旧证据按规则失效；截图顶部状态冲突另列用例核对。
