# AI Native ALM MVP 产品与技术蓝图

- 状态：设计基线，待原型验证
- 日期：2026-10-23
- 产品入口：DeepSeek Harness Desktop
- MVP 试点：单一业务模块的一次跨需求与架构变更

## 1. 产品目标

将需求、架构决策、接口、数据定义和测试依据作为可版本化的研发资产，使其拥有与代码相同的本地工作流：拉取基线、创建工作区、由人或 Agent 修改、运行门禁、提交评审、合并到开发空间、生成不可变发布基线。

用户通过 DeepSeek Harness Desktop 完成研发工作。需求和架构以两个独立插件呈现；变更集、资产关系、门禁和基线由共享研发服务处理。插件负责领域体验，Git 仓库保存源文件和历史，CI 与服务端策略决定是否可合并、发布。桌面应用关闭后，门禁和发布任务仍由服务端持续执行。

首个场景固定为“订单支持部分退款”：同一变更同时修改需求、架构决策、接口/数据定义和验收依据，并经过错误引用拦截、人工评审、开发集成与基线重建。MVP 不以生成文档数量衡量成功，而验证端到端追踪和发布可复现性。

## 2. 用户与核心工作流

主要用户是产品/需求工程师、架构师、测试工程师、评审人和发布负责人。Agent 是受权限约束的协作者，不是审批主体。

```text
需求任务
  -> 解析当前基线与关联资产
  -> 创建本地变更工作区
  -> 需求插件与架构插件协同修改
  -> 结构、关系、安全、渲染门禁
  -> 语义差异与影响范围评审
  -> PR 人工审批、CI 重跑、合并到 develop
  -> 开发空间预览
  -> 发布候选审批
  -> 不可变基线与可校验发布包
```

一次变更必须在一个变更集中提交所有相关资产。审批绑定具体提交 SHA；新提交使针对旧 SHA 的审批失效。已发布基线只读，后续变更必须从基线派生新分支，并记录变更原因。

## 3. 产品范围

### MVP 必须交付

- 需求插件：浏览/查询需求、澄清字段、拆分需求、维护验收条件、查看追踪缺口和差异。
- 架构插件：维护模块、ADR、接口及数据模型引用，查看依赖图、覆盖关系和影响分析。
- 共享 ALM 能力：工作区与变更集、稳定资产 ID、关系索引、语义差异、门禁证据、基线清单。
- 本地 Agent 工具：只读检索、创建变更分支、修改建议、运行门禁、生成差异和提交 PR。所有写入限定在当前工作区。
- Git/CI：以 Gitea PR 和 Actions Runner 承载评审、必需检查、开发分支集成和发布标签。Git 是源文件与版本历史事实源。
- 源文件：需求使用 StrictDoc 可管理的文本格式；架构使用 Markdown/ADR、YAML、OpenAPI 与 Mermaid。HTML 等作为构建产物，不作为第二份可编辑事实源。
- 门禁：格式/Schema、ID 唯一性、关系完整性、需求验收覆盖、禁止直接改已发布基线、渲染成功、依赖和敏感内容检查。
- 发布基线：固定 Git commit、规则版本、工具版本、审批与门禁证据、生成物 SHA-256；能从基线重新生成并核验发布包。

### 明确不进入 MVP

- 自研完整 Git 托管、通用流程/表单引擎、组织目录和权限中心。
- 同时支持多个 Git 托管平台或多个文档格式。
- 自动批准高风险变更、Agent 自审自批、AI 结果直接覆盖发布内容。
- 公网托管 StrictDoc Web 编辑器；试点先通过本地文件和 DSH 工作区操作。
- 双向同步既有 ALM 系统。若需演示，现有系统只接收已发布基线的单向投影。
- 全量替换测试管理、缺陷管理、代码仓库或现有研发门户。

## 4. 插件与领域边界

| 插件/组件 | 责任 | 核心交付 |
|---|---|---|
| `dsh-alm-requirements` | 需求澄清、结构化编辑、验收条件、需求追踪 | 需求浏览/详情/差异视图；需求查询、校验和变更工具 |
| `dsh-alm-architecture` | 模块、ADR、接口、数据定义与需求分配 | 架构目录/依赖视图；架构查询、影响分析和关系校验工具 |
| `dsh-alm-core` | 工作区、变更集、资产 ID/关系、门禁、基线、权限上下文 | 插件共享服务与 UI 面板；CLI/API/MCP 稳定边界 |
| Gitea + CI Runner | Git、PR、保护分支、审批、必需检查、构建 | `develop` 集成空间、发布 tag 和流水线证据 |
| StrictDoc | 需求源文件解析、需求追踪与文档生成 | 可版本化需求文件与构建预览 |

需求与架构插件共享变更 ID 和仓库工作区，不各自建立独立审批流。平台能力应经 core 的版本化服务契约暴露，不让两个插件直接读写对方内部状态。

## 5. 研发资产模型

每项资产有稳定 ID；文件路径可变，ID 不变。第一版资产类型为 `requirement`、`architecture-decision`、`module`、`interface`、`data-model`、`acceptance-test`、`risk`。

```yaml
schema_version: 1
id: REQ-PAY-001
type: requirement
title: 支持部分退款
status: proposed
owner: team-payments
links:
  - type: allocated_to
    target: MOD-PAY-REFUND
  - type: constrained_by
    target: ADR-PAY-003
  - type: verified_by
    target: TEST-PAY-001
```

关系类型至少包括 `satisfies`、`allocated_to`、`depends_on`、`constrained_by`、`verified_by`、`supersedes`。校验器拒绝重复 ID、悬空引用、非法关系方向和已发布基线原地修改。关系图从仓库内容构建，可丢弃并重建，不作为另一个可手工编辑的事实源。

每次门禁生成机器可读证据：基线 SHA、候选 SHA、规则包版本、工具版本、检查项、结果、日志引用和产物哈希。AI 语义审查只提供带文件/资产/位置引用的发现与建议；确定性门禁结果不能由模型覆盖。

## 6. 目标架构

```text
DeepSeek Harness Desktop
  ├─ 需求插件 ───────┐
  ├─ 架构插件 ───────┼─ DSH 插件服务契约 / UI 扩展点
  └─ ALM Core 插件 ──┘
          │ 版本化本地 API / CLI / 可选 MCP
          ├─ Git 工作区、资产解析、关系索引、差异和门禁
          └─ Gitea API 适配器（PR/状态/分支保护）
                    │
          Gitea ─ Actions Runner ─ CI 构建与必需状态检查
                    │
          不可变发布存储：manifest + 文档包 + SHA-256
```

采用模块化单体/本地服务作为 MVP 的共享核心，领域模块通过版本化接口隔离。先避免拆微服务带来的部署和事务复杂度。Git 仓库保存资产内容；Gitea 保存协作事实；构建产物存储保存不可变发布包。发布清单以 commit SHA 为主键，标签只是可读定位符。

DSH 插件注册、服务依赖、UI slot、热更新和桌面权限 API 在官方仓库中处于快速演进阶段。实现前必须针对用户实际安装版本确认 API、示例、许可和打包方式；在 API 未验证前，core 的 CLI/API 作为可独立测试的边界，插件通过薄适配层集成。

## 7. 信任、权限与可靠性

- Agent 工具默认只读；显式创建工作区后，写权限限制在该分支和允许目录。
- Agent 不得修改门禁策略、保护规则或发布存储，不得批准自己的提交，不得发布高风险变更。
- 本地检查给出快速反馈；服务端重新运行同一版本规则并决定合并/发布。客户端结果不能作为服务端通过证据。
- 所有外部写入在调用前展示目标仓库、分支、变更范围和动作；写入后回读并核对服务端状态。
- 权限按仓库/项目过滤资产检索与工具执行；秘密不进入提示上下文、生成文档或审计正文。
- CI 任务幂等、可重试，发布写入不可覆盖；失败时保留候选记录和可诊断日志，不创建半成品正式基线。
- 每个发布包包含工具/规则版本、源 commit、生成时间、文件清单与校验值；恢复操作通过选定旧基线重新部署，不改写历史。

## 8. MVP 实施阶段

### 阶段 0：兼容性与垂直切片

固定 DSH Desktop 版本，按官方插件开发文档创建一个最小插件，验证加载/卸载、工具注册、插件间服务依赖、UI 扩展、权限提示和错误恢复。完成一个本地仓库读取和 `alm check` 调用。若关键扩展点不可用，先交付 CLI + MCP 原型并记录桌面插件适配缺口。

### 阶段 1：资产规范和确定性门禁

建立部分退款样例仓库、Schema、ID/关系校验器、语义化 diff、渲染脚本和固定测试数据。实现重复 ID、悬空关系、缺少验收条件、非法状态和基线修改的反例。

### 阶段 2：需求与架构双插件

两个插件分别实现清单/详情/差异视图与领域工具，共用 core 的工作区、资产查询、变更 ID 和门禁证据。演示一次跨插件联合变更，不要求两个插件分别提交或审批。

### 阶段 3：评审、集成与发布

接入 Gitea PR、受保护 `develop`、CI 必需检查和人工审批。合并后生成开发空间预览；发布候选通过审批后创建不可变基线和发布包。验证提交变化使旧审批失效。

### 阶段 4：试点评估

由产品、架构、测试和发布角色共同完成三次变更演练（正常、门禁失败修复、发布回滚/重建）。记录操作耗时、人工介入、AI 建议采纳率、漏检/误报和恢复结果，评审是否进入下一模块。

## 9. 验证方案与验收

### 功能验收

1. DSH Desktop 可安装并启用两个业务插件；两个插件读取同一基线并操作同一 ChangeSet。
2. Agent 能从指定基线拉取需求/架构依赖闭包，创建分支，修改部分退款样例并提交 PR。
3. 合法变更全部通过门禁；重复 ID、悬空关系、未覆盖验收、格式错误、秘密扫描命中均阻止合并并定位资产。
4. PR 页面能看到源/目标 SHA、结构化差异、影响资产、门禁证据和 AI 发现引用；缺少人工审批不能合并。
5. 新提交后旧审批不可用于合并；Agent 身份不能批准自身变更或更改分支保护。
6. 合并到 `develop` 后可生成预览；发布审批后生成含源 SHA、规则版本、审批记录和文件哈希的不可变基线。
7. 从任一基线重建文件包，清单和 SHA-256 一致；回滚只切换当前发布指针，不修改基线内容。

### 质量与稳定性门槛

- 资产和关系确定性校验 100% 覆盖已定义硬规则；AI 输出不参与通过率统计。
- 正例端到端流程连续成功 10 次；每类负例均能稳定失败，修复后可重跑通过。
- CI 失败、网络中断和重复 webhook 不会产生重复正式基线或丢失审计记录。
- 试点资产检索 P95 < 2 秒；本地结构/关系门禁在 1000 项资产样本上 P95 < 10 秒（MVP 目标）。
- 所有写入动作具备审计主体、目标、SHA、时间、结果；所有发布包可离线校验。
- 插件 API 契约测试在目标 DSH Desktop 版本上通过，并记录版本号；升级宿主时跑兼容性回归。

### 验证层次

| 层级 | 验证内容 |
|---|---|
| 单元 | Schema、ID、关系方向、影响闭包、语义 diff、基线清单哈希 |
| 集成 | 临时 Git 仓库、Gitea API/PR、CI 状态、审批过期、失败重试 |
| 插件契约 | DSH 插件发现、服务依赖、工具 schema、UI 生命周期、权限错误 |
| 端到端 | 部分退款正例与负例，从工作区到 PR、develop、基线重建 |
| 安全 | 越权查询、目录逃逸、提示注入来源、秘密泄漏、自审批、规则篡改 |
| 恢复 | 宿主重启、Runner 中断、重复回调、发布失败、旧基线重建 |

## 10. 决策与风险

| 风险/待验证项 | 处理方式 |
|---|---|
| DSH Desktop 插件 API 仍可能变化 | 阶段 0 固定宿主版本并做真实安装验证；隔离 DSH 适配层 |
| StrictDoc 的 Web 服务部署边界 | MVP 先用本地文件/构建器；公网服务需单独安全评估 |
| Gitea 功能与部署版本差异 | 固定 Gitea/Runner 版本，以必需状态检查和旧审批失效做验收 |
| 结构化格式和语义 diff 设计过早 | 只覆盖试点资产类型；保留 Markdown 与 YAML 源文件可读性 |
| AI 影响分析不完整或不稳定 | 关系图确定性闭包作为底线；AI 只能补充候选项并给证据 |
| Git 与下游门户双主冲突 | 仓库为源；发布系统只接收单向、可重复同步的基线 |
| 插件跨版本兼容成本 | 插件 manifest 与 core 服务契约独立版本化，维护最小支持矩阵 |

首轮完成后再决定是否把 GitHub 现有仓库工作流迁至 Gitea、是否建设服务端资产注册 API，以及是否扩展测试/质量插件。MVP 阶段不要求迁移本仓库的 GitHub 工作流。
