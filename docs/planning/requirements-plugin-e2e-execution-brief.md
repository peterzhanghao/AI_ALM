# DSH 需求插件端到端验证与优化执行指令

用途：将下方“执行指令”完整交给 DSH Harness。它要求实际推进一次小型需求，并生成可由人和 Codex 分别审阅的证据包。

本文件是执行任务书，不是验证结果。编写日期：2026-11-03。端口、模型、版本和实现行为均以执行当时发现的事实为准。

你是 DSH 需求插件的端到端验证负责人，同时具备产品走查、开发执行和故障定位能力。请实际操作当前需求插件，验证“用户表达意图 → 澄清与确认 → 需求入库 → 授权 AI 推进 → 真实开发 → 测试与修复 → 交付候选 → 人类验收入口”的完整闭环，并输出可打开的报告页面和可交给 Codex 分析的报告包。

目标是发现并解决真实推进障碍。必须用真实行为和可核验产物支撑结论；创建任务卡、得到 HTTP 200、执行会话调度成功、模型自述完成、通用测试通过，都不能单独证明需求已经实现。

### 1. 工作范围与执行纪律

1. 默认仓库为 `D:/DSH`，实际路径先确认。读取适用的 `AGENTS.md`、插件 README、当前实现与启动帮助。历史报告仅作线索，不继承其通过结论。
2. 本任务授权：创建隔离测试项目、使用现有模型执行一次受控小型开发、收集证据、编写复跑脚本，以及修复当前仓库中与本轮推进直接相关的最小插件缺陷。先保留失败证据，再修复、开新轮复验。不重构无关模块。
3. 仓库可能存在大量未提交工作。先记录 staged/unstaged/untracked 基线；保留既有修改和暂存状态，不执行清理、重置或覆盖。不要只从 HEAD 创建测试副本而丢失本轮正在测试的未提交插件代码。
4. 业务开发发生在独立测试项目；插件修复发生在插件仓库。记录这两个根目录、宿主实际安装路径及模型执行工作区，防止串写。新的分支按适用仓库规则命名。
5. 不自动提交、推送、创建远端 Issue/PR、合并或部署。默认只验证发布预览和授权门禁，真实远端发布不在本轮范围。已有明确授权则按授权执行，并单独记录。
6. 不代替真实人类签收，也不以 `human:*` 伪造身份。验收入口、退回、发布授权的自动化测试使用隔离数据和明确的测试身份；无法区分测试身份的实现，使用独立契约测试验证，真实签收保持待人类处理。
7. 不把环境限制转写成产品通过；缺浏览器、模型或真实宿主时，完成独立可执行检查，记录阻塞、缺失范围和恢复方式。

### 3. 固定一个能真正开发和展示的小型业务场景

优先选择独立测试项目中的轻量任务列表。若没有现成项目，准备一个无需外部账户的最小可运行页面：初始已有任务数据、标题和状态，搜索与状态筛选尚未实现。基线准备脚本不得提前实现待测功能；保存基线快照与功能缺失证据。项目仍通过需求插件正常关联和打开。

向插件输入这段意图，不直接写正式需求文件：

> 我想在这个任务列表里按标题查找任务，同时按“全部、待处理、已完成”筛选。搜索与状态筛选要一起生效；输入前后空格应忽略，英文搜索不区分大小写。没有结果时要明确提示，并提供清空条件的入口。保持现有任务数据和状态，不需要登录、云同步或发布。

在首次确认前固定以下验收条件，逐项编号，不得在执行中降低标准：

| 编号 | 可观察结果 |
| --- | --- |
| AC-01 | 输入部分标题，仅显示匹配任务；清空后恢复 |
| AC-02 | 切换三种状态筛选，结果与固定测试数据一致 |
| AC-03 | 搜索和状态同时生效，取交集 |
| AC-04 | 空格与英文大小写按原意图处理 |
| AC-05 | 零匹配显示明确空态，清空条件后恢复全部数据 |
| AC-06 | 刷新后原有任务及状态未被搜索操作破坏 |
| AC-07 | 搜索、筛选和清空控件可通过键盘使用；约 720px 宽度下主流程可达 |

准备包含相似标题、不同状态、中文和英文的确定性数据，并给每条 AC 写出精确预期结果。验证器独立读取这些预期；不能仅检查输入框存在。先在基线上证明新增功能至少一条业务断言失败，再由插件调度的真实 AI 执行实现，最后证明同一断言通过。

### 4. 按真实操作完成主链路

| 阶段 | 真实动作 | 必须核验的事实与证据 |
| --- | --- | --- |
| E2E-01 项目入口 | 从宿主打开需求插件并选中隔离项目 | 项目根正确；空态/列表可操作；记录入口截图与工作区信息 |
| E2E-02 意图输入 | 通过界面输入上述原话并分析 | 真实模型调用有结果；原话可追溯；区分事实、推测和待确认项；未确认前无正式需求新增 |
| E2E-03 澄清与范围 | 必要时回答会改变方案的问题，核对范围和 AC | 不强迫无意义问卷；不偷加登录/云服务；手工编辑字段在后续问答中保留 |
| E2E-04 确认入库 | 确认实际推荐路线和交付范围 | 从 UI 回执读取真实 INT/REQ 标识；核对落盘内容、修订和 AC；重放不重复创建 |
| E2E-05 AI 接手 | 点击当前真实主按钮，如“交给 AI 推进” | 自动 preflight；登记变更；真实 RUN/session 调度回执；工作区正确；非仅生成 CHG/任务卡 |
| E2E-06 开发执行 | 等待真实 AI 读取、修改、测试和修复 | 会话工具记录、业务代码实际 diff、切片检查点、真实 stdout/stderr/exit code；观察至少一次运行中状态 |
| E2E-07 持续推进 | 关闭面板再打开，或刷新并重新进入 | 同一运行可追踪，不重复派单；进度反映实际执行；有问题时明确下一步 |
| E2E-08 业务验证 | 打开 AI 交付的真实业务页面并执行 AC-01…07 | 独立浏览器断言、前后对照、截图/DOM；新增行为真实生效；通用测试不能替代业务断言 |
| E2E-09 交付候选 | 从插件进入交付/验收界面 | 当前 CAND 关联 REQ、实现版本与本轮有效证据；显示待验收和准确预览入口；不自动变成人类已验收 |
| E2E-10 验收交接 | 查看实际验收入口与候选信息 | 人能看到改了什么、如何验证、未决问题、验收/退回操作；真实决定可待人类处理 |
| E2E-11 报告交接 | 生成并打开本轮报告 | HTML 可离线打开；证据和问题可定位；Markdown/JSON 与页面结论一致 |

“正常推进”的判断：没有无出口弹层；每一步成功后能进入下一步；失败或等待时能看到原因、当前对象、可执行恢复动作。已调度不等于已开发，run 结束不等于 AC 通过，测试通过不等于人类签收。

主链路必须走真实 UI + 真实模型 + 真实宿主执行器 + 真实文件与业务页面。API、桩或手工写文件可帮助定位和补充测试，均需单独标记，不能补写成主链路通过。如果验证者直接替宿主执行器写完业务功能，这一轮只能算旁路诊断，应恢复独立基线并重新验证执行链路。

### 5. 失败恢复和边界矩阵

在主链路之外，为以下场景使用独立副本，避免相互污染。每项记录注入方法、预期、实际、恢复动作与恢复后的状态。真实链路未执行的部分，保留为未验证或部分通过。

| 编号 | 场景 | 必须验证 |
| --- | --- | --- |
| NEG-01 | 明确意图/模糊意图/仅咨询/复用已有需求 | 选择合适路线，未确认不入库；咨询和复用不无故新建 |
| NEG-02 | 双击确认、双击推进、网络响应丢失后重试 | 同意图不重复建需求，同一次推进不重复建活跃 run；请求冲突可解释 |
| NEG-03 | 验收在实现前失败 | 失败作为开发输入，不因尚未实现永久阻止开发；执行后重跑有效测试 |
| NEG-04 | 模型超时、执行载体不可用 | 真实错误可见，不假装推进；有限重试有次数、原因和最终结果 |
| NEG-05 | 受控业务歧义，回答并继续 | 独立测试意图主动保留一处规则取舍；进入 needs-input、保留检查点；仅用预先定义的测试答案继续，不伪造真实业务决定 |
| NEG-06 | 取消、重新开始、宿主中断 | 取消后工作保留且不继续写；过期心跳不永久显示运行；恢复关联前序记录；仅中断自己创建的隔离宿主 |
| NEG-07 | 候选生成后改变相关需求/代码/测试 | 旧证据或候选不再满足当前验收条件；旧签收/发布授权不能应用到新候选；历史记录保留 |
| NEG-08 | 切换工作区、同 ID 不同文件、陈旧修订 | 不串写、不静默覆盖；冲突能定位到工作区、文件和修订 |
| NEG-09 | 产品缺陷/执行环境失败/用户取消 | 分类准确；产品缺陷有记录与去重；确认前不擅自修复新缺陷需求；恢复后能复验 |
| NEG-10 | 从错误页提交反馈并处理 | 反馈带现场、对象、错误与版本；回执能读回；关联问题；测试通过不自动把原反馈标为已解决 |
| NEG-11 | 人类验收和发布门禁 | AI 采纳不等于人类签收；无授权不能真实发布；默认仅预览。独立门禁测试与实际人类操作分开统计 |
| NEG-12 | 窄屏/键盘/空态/错误态 | 主按钮可达，弹层可退出，焦点可恢复；不以截图替代行为断言 |

默认预算：主链路 30 分钟；每个外部模型失败最多重试 2 次；单阶段连续 3 次无进展则停止该分支并出具诊断；最小插件修复最多 2 轮。预算到达不宣称完成：保存现场、恢复指令和剩余工作，再继续其他独立检查。实际消耗与调整原因写入报告。

### 6. 插件问题的修复与复验

先以失败轮记录问题，不边改边覆盖证据。每个问题给出稳定 ID、复现步骤、最早失败环节、用户影响、期望/实际、相关日志、根因假设与置信度。区分插件实现、宿主兼容、模型外部依赖、被开发业务产品、测试驱动错误和需求歧义。

证据充分且在授权范围内的插件缺陷，做最小修复并加入针对性回归。记录修复 diff，确认新宿主/客户端加载实际新版本，再开新轮。重跑失败场景、关联受影响场景和主链路；不要只运行新增单元测试就宣布端到端已恢复。没有在新版本复现的假设只能称“待核验”。

### 8. 结论和完成标准

每个场景只能使用 `passed / failed / partial / blocked / unverified / not_applicable`：

- `passed`：本轮规定范围完整实测，断言全满足，证据齐全。
- `failed`：实际行为与明确预期不符，即使另一次重试成功，失败尝试仍保留。
- `partial`：只完成部分步骤或只覆盖部分环境；必须列缺口。
- `blocked`：因明确前置条件无法执行，给出阻塞和恢复方式。
- `unverified`：未执行，或只有实现/单元测试痕迹。
- `not_applicable`：有明确理由不适用；不得用于隐藏必需主链路。

保留每次尝试，不能用重试后的通过抹掉模型不稳定。统计按场景和尝试分别计算，不把截图数、断言数、单元测试数混为通过率。明确必需场景分母及部分/阻塞/未执行数量。

总体分开输出三个结论：

1. **技术端到端结论**：完整主链路和所有 AC 均有真实证据，才能标记 `passed`；缺真实执行器、真实宿主交互或业务验证时不能通过。
2. **扩展覆盖结论**：失败恢复、门禁、兼容性等矩阵的实际覆盖与遗留问题。技术主链路通过不表示扩展矩阵全部通过。
3. **人类验收/发布状态**：明确 `pending_human / accepted / rejected / not_requested`，只引用真实人类决定；默认真实发布为 `not_requested`，预览另列结果。

任务完成是“拿到可信结论和可复查证据”，不要求把所有问题包装成全绿。仍存在阻塞时也必须生成完整报告和 Codex 交接包。

交付前检查：JSON 可解析且 ID/证据引用可解析；统计可重算；HTML 离线打开无断链；图片真实存在；复跑说明可执行；最终源码与最后一轮指纹一致（若不一致明确标记证据过期）；不包含凭据；输出实际报告入口和遗留问题。
