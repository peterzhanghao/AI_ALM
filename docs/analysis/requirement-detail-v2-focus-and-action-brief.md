# 需求详情重构：清楚的需求、可信的现状、唯一的下一步

日期：2026-11-03。交付性质：静态审查、产品方案与开发执行指令；未修改插件实现，未复现截图对应运行。

## 1. 核心判断

当前详情把各功能模块的内部状态直接铺到页面：执行、证据、缺陷、归属、版本分别生成自己的卡片、文案和操作。功能逐步增加，首屏不断增加模块，却没有统一“用户此刻要读什么、决定什么”的组织规则。

信息轰炸来自四种负担：同时处理多个语义维度、辨认重复信息、调解看似矛盾的状态、从多个按钮猜测正确行动。只减字号、增大抽屉或把所有区域折叠，均不足以解决。

页面的任务应收敛为：**理解这条需求承诺什么，知道当前发生什么，在需要时完成下一项决定。**

推荐以“单列正文 + 当前待办 + 三个按任务分区的页签”替代默认双列卡片仪表盘。保留证据与追溯能力，通过明确入口逐步展开。

### 证据边界

依据：用户本次截图，D:/DSH 当前 `client.js`、`query.mjs`、`preflight.mjs`、`evidence/decision.mjs`、`requirements/delivery.mjs`，以及既有详情评估文档。旧文档的实施与测试结果仅为历史资料；当前截图和当前源码优先。未进行用户研究、宿主交互复现或本次 UI 测试，不声称已经证明可用性提升。

## 2. 问题与根因

| 观察 | 影响 | 重构要求 |
| --- | --- | --- |
| 标题已有“待推进”，状态卡再次列“交付状态”；等待回答与中断原因重复 | 用户花精力重复确认同一事实 | 标题显示身份，当前待办用一句话解释情境 |
| 顶部状态、DecisionBar、footer 分别决定动作 | 等待回答时仍出现泛化“交给 AI 推进” | 同一状态投影产生一个主动作，不能各写一套 if |
| 红色阻塞、黄色缺陷边框、P1、风险高同时强调 | 优先级、阻塞、历史事件都像正在报警 | 只突出当下需要处理的真实事项，历史保持低强调 |
| 缺陷已关闭仍有大型黄色卡片 | 历史结束事件抢占当前工作；易误读为需求关闭 | 关系中一行呈现或进入记录页，真实回归另行提示 |
| 验收失败、评审 0/5、AI 评审阻塞、建议已采纳并列 | 不知是否同一次、同一版本、同一种评审 | 标明证据对象、时效与不同评审通道，不强行合并 |
| 四个 TEST ID 在证据区与归属关系列表重复 | 识别码数量盖过“验收要求是什么” | 显示可读验收条件，关联用例改为数量与展开入口 |
| 需求目标和范围在证据、路径、归属等模块之后 | 详情先讲系统如何管理它，再讲它要做什么 | 默认“需求”页优先展示目标、范围、验收要求 |
| 路径、hash、规则码和具体时间常驻首屏 | 技术溯源挤占决策信息 | 最近更新时间用低强调文案，完整引用在证据详情 |
| 正文里出现“与背景相同，已合并显示”等解释 | 产品内容被渲染器说明打断 | 正文不呈现去重过程，原始内容可追溯 |
| 几乎所有块都是同等重量的卡片 | 缺少稳定阅读顺序 | 少量表面层级，用标题、留白、分隔线组织内容 |
| 880px 抽屉仍分 1.6:1 两列 | 主文变窄、侧栏密集换行 | 默认单列，不随屏幕变宽自动增加常驻元数据栏 |
| 背景大面积模糊且不可用 | 保留了列表占位，却失去列表的上下文价值 | 先保留一致模态，去掉重模糊；不做半模态混用 |

### 代码层需要优先修正的语义

1. `CurrentStateStrip`、`primaryActionFor/DecisionBar`、`DrawerContent` footer 分别含状态与动作逻辑；服务端 query 另有 nextAction。应统一可操作情境的投影，保留后端写入时重新校验。
2. 当前 footer 通过 delivery 判断是否等待输入；delivery 目前会把等待人类输入的 run 回退为 pending。若 footer 只在 in-progress 分支处理 waiting-input，就有走到泛化启动动作的风险。截图与此风险一致，但实际 API 行为须运行核验。
3. `riskLevel` 主要把 P0/P1 映射为 high，不能把这个标签当独立诊断出的“风险高”。保留必要评审策略，显示“P1 · 按策略需 5 个评审视角”时按需解释，不另造风险评价。
4. startReadiness 区分“进入开发”与“达到验收”：既有验收失败可带入开发修复，并非所有红色证据都应禁用开发。旧文档里一律阻止开工的规则不能直接照搬。
5. 正文去重使用前缀覆盖比较，存在把“相同开头但多了限制”的长段隐藏的风险。简洁呈现不能损失已确认语义。
6. `isAiSection` 用 AI/评审/重构/建议等标题正则分类，可能误把用户自己写的“重构范围”当 AI 建议。内容来源应按元数据判定，旧数据不能仅凭关键词推断作者与可信度。

## 3. 方案选择

| 方案 | 好处 | 局限 | 结论 |
| --- | --- | --- | --- |
| 保留所有卡片，只改配色与间距 | 成本小 | 多套动作与信息优先级不变 | 不作为主方案 |
| 单页全部折叠 | 初看更短 | 用户要不断猜内容藏在哪，阻塞易被藏住 | 仅用于次级证据 |
| 放大全屏双栏工作台 | 可容纳长内容 | 仍可能同时轰炸，失去快速查看的轻量感 | 长任务可选展开，不强制 |
| 单列 + 当前待办 + 需求/交付/记录 | 阅读顺序稳定，操作与正文分开，保留深入检查 | 需要统一状态与导航 | 推荐 |

三页签按用户任务划分，不按数据库表或内部模块划分。默认打开“需求”；从明确的运行/验收入口进入时可打开相应交付内容。不能因后台状态更新自动切页签。

## 4. 可直接交给 Harness 的开发执行指令

以下为实际插件重构任务。先核对当前实现，再按下述目标开发和验证。复用现有需求、运行、证据、反馈与缺陷能力，保护工作区未提交修改，不重写交付状态机，不引入额外平台。

### A. 页面骨架

```text
REQ-ALM-001 · v1                         [反馈] [更多] [关闭]
需求查询条件和列表优化
张浩 · P1 · DSH（ALM）                         [详情]

需要你回答
显示当前真实决策问题的短摘要；若拿不到正文则明确说需要查看。
[查看问题]                         主动作固定在底部
──────────────────────────────────────────────────────
需求                 交付 · 有待处理事项                 记录

目标
真实的目标内容，不从页面标题编造。

范围
本次包含什么；已明确的不包含什么。

验收要求
可观察的条件和预期结果；缺失时明确提示。
查看关联用例（4）

背景与原始诉求（按需展开）
──────────────────────────────────────────────────────
正在等待你的回答                    [回答并继续]
```

这是结构示意，截图中的具体问题、统计与正文必须来自真实数据，不能照示例写死。

### B. 标题区只保留身份与必要元信息

- 第一行需求 ID、修订与低强调工具；第二行标题；第三行负责人、优先级、项目合并为普通文字，避免全部胶囊化。
- 需求 ID 点击复制或使用无歧义的小复制按钮；复制路径位于元信息详情。
- 关闭入口保留一个，放标题右侧。不要底部再次占用按钮位置。
- “更多”收纳归档、删除、复制提示词、打开源文件等低频操作。删除与归档保留现有真实语义及确认机制，不能改成视觉隐藏后绕过检查。
- 标题优先完整换行；不能为了首屏强制把关键标题裁掉。

### C. 用一块“当前待办”替代多块状态总览

该区域最多显示：一个情境标题、一到两句解释、一个次级查看入口。完整信息按需进入交付页。

情境表达示例：

- “需要你回答”：有有效的当前决策请求，展示真实问题摘要。
- “AI 正在开发”：有真实活动 run，显示当前阶段与最新有效活动时间，不虚构百分比。
- “推进已中断”：失去心跳或真实执行失败，说明已知原因与可恢复性。
- “需求需要修改”：当前有效评审存在阻塞，概括有依据的主要问题。
- “等待验收”：当前候选已满足相应前置条件，标明需要人工验收。
- “已验收”：说明验收绑定的候选；发布状态独立，不能推导为已发布。
- “尚未开始”：无活动 run 与当前决策请求，提供真实下一步。
- “已关闭”：展示关闭原因；关闭可能是取消或重复，不一律说已完成。

正常状态可以是轻量文本行；需要用户介入时才使用有色侧边线或轻背景。已关闭关联缺陷、历史失败和未建立 GitHub 关联不能各占告警卡。

不把所有状态压成一个万能 status：交付、执行、评审、证据、缺陷仍是独立事实，当前待办只是投影。严重数据异常或证据冲突必须有明确入口，不能被主情境掩盖。

若 AI 正等待用户回答，当前待办应优先展示它正在等的具体决定；其他评审阻塞在交付页保留。是否允许带着阻塞继续，仍由当前授权和后端规则校验，不能以操作优先级绕过业务规则。

### D. 一个主动作，一份判定

建立纯函数/共享业务投影，例如 `deriveDetailView`，名称按项目约定调整。输出应包含：

```text
identity + revision
context: headline / explanation / tone / relatedRefs
attentionItems[]: 类型、是否当前、影响、引用
primaryAction: actionId / label / enabled / reason / targetRef
secondaryActions[]
reviewSummary / acceptanceSummary / deliverySummary
freshness: 证据版本、候选版本、读取时间与缺失信息
```

由同一投影决定待办、footer、页签提醒和列表中的等价操作。复用现有 query nextAction 时先检查其业务覆盖，不能把显示建议直接当授权接口。

主动作绑定工作区、稳定需求实例、当前需求修订、run/decision/candidate ID 与必要版本。点击时后端重新校验；状态已变化则告知并刷新，不能把回答发给新问题或验收错候选。

| 实际情境 | 主动作 | 必须避免 |
| --- | --- | --- |
| 有有效且待答的 run 决策 | 回答并继续 | 重新冷启动另一条 run |
| 有检查点且可恢复的中断 | 恢复推进 | 保证不会重做任何工作而无证据支持 |
| 代理正常交回且无明确问题 | 查看本轮结果/继续推进，按真实能力决定 | 误称必须回答某个不存在的问题 |
| 活动开发 run | 查看运行 | 同时提供可点的重新启动 |
| 当前评审阻塞 | 查看并处理问题 | 采纳建议直接当成阻塞已解除 |
| 无活动运行，验收失败可作为开发任务 | 开始修复，走现有 preflight | 因测试红而永远禁止修复开发 |
| 当前候选待人工验收 | 验收交付 | 继续显示开始开发 |
| 已验收且有发布动作 | 决定发布/查看发布，依据权限和真实记录 | 自动发布或标已发布 |
| 本需求自身缺陷待确认 | 处理缺陷需求 | 把关联源需求的缺陷状态当本需求授权 |
| 数据关系歧义或版本冲突 | 核对数据/刷新 | 猜测目标文件并继续写入 |
| 已关闭 | 无推进主动作 | 把关闭等同开发成功 |

这张表是情境参考，不是绕过当前规则的固定优先级。组合状态须写明确测试，例如“等待回答且评审阻塞”“已关闭缺陷但需求未验收”“活动 run 与过期候选共存”。

页内不重复放第二个同名强按钮。当前待办的“查看问题”只导航到正文或面板；footer 的“回答并继续”进入回答流程，回答未经用户提交不得恢复运行。

取消运行属于运行控制，放交付页次级操作或运行菜单；是否可取消依据真实状态。没有可靠取消能力时明确说明，不伪装停止。

### E. 三个页签的信息内容

#### E1. 需求：先让人读懂承诺

依次展示目标、范围、验收要求；背景、原始诉求、约束、附件按相关性组织。简短内容直接显示，长背景默认收起。不要把完整需求正文全藏在折叠里。

原始文本没有目标、范围或验收时，只说“尚未明确”，给已有编辑/澄清入口。不能由摘要器临时生成已确认需求；不在每次打开时调用模型改写正文。

现有材料只有标题与背景时，仍需清楚显示已有内容和缺失，不用空卡片把页面填满。为缺失关键信息给一条合并提示，避免三条相同红警告。

区分：

- 验收要求：软件应呈现什么行为。
- 关联测试用例：哪些测试用于验证。
- 最近执行证据：它们什么时候对什么版本运行，结果如何。

需求页呈现前两者的简洁摘要，实际执行结果在交付页。关联四个 TEST ID 不等于四项验收已通过；链接的数量不等于通过数量。

只对规范化后完全相同的内容做可逆展示去重，不能用前缀相同判断一段可以消失。保留原文查看入口；正文无需打印去重过程说明。

AI 建议以来源元数据区分，不能用标题中有“重构/建议”就判 AI 内容。已采纳意见若已成为正式需求条款，应在正文展示其当前有效内容，记录中保留来源；未经采纳的建议不能混成承诺。

#### E2. 交付：集中处理执行、问题与证据

显示当前运行摘要、待答问题、当前有效阻塞、交付候选、评审摘要、验收执行摘要。使用简洁分组和列表，避免每组再嵌套多张卡片。

当前决策问题默认展开，已有阻塞按数量摘要并可展开。重要问题不得只藏在一个无提示的页签中；其他页签通过当前待办与“交付 · 待处理”提示其存在。

一个事实只保留一个完整版本。顶部说明与页内摘要是导航摘要，不反复打印同样长的错误和修复文案。

不同评审通道保持命名和范围：规则/视角检查与 AI 语义评审分别显示；AI 评审已存在时不能把全局写成“未评审”。覆盖为 0/5 只说明对应策略要求的视角覆盖，不能表示该需求有 0% 质量。

若“已采纳”与“仍阻塞”并存，解释为“建议已采纳，阻塞尚未解除”，并展示当前有效报告与需求修订。采纳不等于通过，人类验收不等于测试命令通过。

验收执行摘要显示结果、证据是否适用当前候选、最近执行时间。完整 hash、命令、报告、环境、规则码与日志放一次展开详情；原始技术值保持可复制。

缺陷用可读关系列表显示：本需求衍生缺陷/本需求关联缺陷/本需求就是缺陷，不能混用。已关闭缺陷为中性历史项；只有新回归证据时重新突出。关闭原因若无记录，不宣称已经修复并验证。

#### E3. 记录：信息与来源可追溯

显示创建、需求修订、关键决定、评审、运行、验收、缺陷与发布的关键事件，按真实时间顺序组织。去重同一事件，标记来源和关联版本，点击查看产物。

需求修订、Git 提交、验收候选、执行 run 是不同对象，不造一条虚假的线性版本史。记录不足明确说明，不以“暂无 Git 提交”推断没有任何需求操作历史。

归属详情、关系、GitHub、源文件与技术信息在此或标题的“详情”子面板中各保留一个规范位置；快捷入口跳到该位置，不复制一套内容。

多个状态来自不同快照时呈现真实读取边界与时效；无法判断当前有效性显示“需要核对”，不擅自取时间最新的单条记录覆盖其他事实。

### F. 视觉与容器规范

保持宿主深浅主题和字体，不另造展示型品牌。复用已有颜色变量，不用大面积红黄背景、渐变或玻璃效果。

建议设计基准：

- 抽屉默认宽约 800–880 CSS px，最大受宿主实际可用区域限制；提供可选展开阅读，不强制全屏。
- 单列内容，正文最大行宽约 640–720px；内部留白 24–32px。
- 标题 20–24px；正文 14px，行高约 1.65；辅助信息 12px，不通过缩成 10px 塞进首屏。
- 8px 间距基准，内容分组间隔约 24px；最多两层表面色。优先分隔线和留白，不用全卡片包裹。
- 正常信息中性；需要决定用克制强调；真实错误用错误色。颜色必须有文字说明。
- 保留一个固定 header、一个内容滚动区、一个固定 footer。footer 是 flex 布局的独立兄弟节点，不放在长正文末尾依赖 sticky 偶然可见。
- footer 通常为主动作和一行简短上下文；动作说明/授权范围放到实际启动、验收或发布确认流程中，不常驻一整行通用免责声明。
- “隔离 worktree”移动到启动配置，标签按实际行为解释，例如“在独立工作区开发”；不改变默认与授权语义，不对不支持的运行方式展示假选项。
- 背景遮罩降低干扰且默认取消重模糊，仍保持模态不可交互；若改为非模态分栏，必须同步改焦点、aria 和背景交互，不能视觉非模态却行为模态。
- 小于约 640px 或高缩放时全屏单列，页签可达、底部安全区正确。所有内容根据容器宽度适配，而非只看显示器宽度。

页面的识别特点是“明确的当前待办 + 可读的需求正文”，不依赖花哨视觉。

### G. 导航、状态与反馈

- 直接打开详情默认需求页；从验收/运行/记录链接进入可深链到对应位置；打开时不自动执行任何操作。
- 切换页签、进入证据或回答流程再返回，保留各页签位置、未提交输入和当前需求实例。
- 切换需求时校验异步响应目标，旧需求数据不闪到新需求；不以可能重复的业务 ID 单独作为缓存键。
- 同一需求后台更新只刷新相应片段，不自动切页签、回滚滚动位置或抢输入焦点。
- 回答、验收、反馈优先复用现有面板；避免“抽屉之上再开抽屉，再开弹窗”。确需对话框时只能最上层接收焦点与 Escape，关闭后回到触发点。
- 数据加载、部分失败、缺少权限、历史读取失败要区分。某个次级模块失败不清空整页，也不默认显示成功或 0 条。
- 页签使用正确语义和键盘操作；模态维持焦点约束与返回焦点。状态变化只在必要时温和播报，不每次轮询全文播报。
- 遮罩关闭和 Escape 不丢失正在编辑内容；按现有保存语义妥善提示。关闭详情不取消开发 run。
- 保留已有反馈入口及其上下文快照能力，重构组件后仍能携带所在页签、需求与当前事件。

### H. 技术实施要求

先梳理并覆盖当前入口：列表行、详情、评审、验收、缺陷、反馈、运行恢复与发布。可复用组件按职责分离，例如：

```text
RequirementDetailShell
  DetailHeader
  CurrentTaskSummary
  DetailTabs
    RequirementContent
    DeliveryWorkspace
    RequirementRecord
  ContextActionFooter

共享：deriveDetailView / capability + evidence adapters
```

这不是要求引入新框架。当前 React 模块加载方式、宿主主题与文件存储保持可用。

优先将动作投影与内容适配抽为可测试纯函数；UI 不自行修补数据状态。服务端授权、幂等、证据版本与当前候选校验继续生效。

纯读取不运行模型、不自动评审、不执行测试。数据按需加载，已有摘要立即展示；进入记录/展开日志时再读较重内容。不要为每个页签新增重复全量扫描请求。

无对应 API 的动作先明确适配方案；不显示点了只弹“开发中”的假入口。删除既有功能前提供新归属与实际可达路径。

### I. 交付顺序

1. **先统一动作和语义。** 覆盖组合状态，修正风险、评审、缺陷和证据的表述；不先靠 CSS 隐藏冲突。
2. **再实施新骨架。** 标题、当前待办、三页签、单列正文和独立 footer；保留数据、交互与反馈。
3. **迁移二级功能。** 证据溯源、问题、历史、关系、文件、worktree 配置、归档/删除都有规范位置。
4. **验证真实场景。** 对照本次截图案例及组合夹具，在真实插件链路检查动作、正文、恢复和可访问性。

### J. 验收标准

功能与状态：

1. 等待回答且 delivery=pending 时，主动作正确进入原 run 决策，不启动新 run。
2. 等待回答与评审阻塞并存，两者均可找到且不互相覆盖；继续执行不绕过后端规则。
3. 活动开发、代理交回、暂停、心跳失联、执行失败分别正确显示。
4. 验收失败但允许修复开发时，不因旧红色证据永久锁死；preflight 规则不被视觉重构改写。
5. 候选过期/证据过期不能当成当前验收通过；人工签收和发布仍独立。
6. 缺陷已关闭但源需求未验收，页面不显示需求已完成、不突出历史黄色告警。
7. AI 建议已采纳但有效评审仍阻塞，解释清楚，无虚假绿色“已通过”。
8. P1 不被单独描述成已诊断出的高风险；相应评审策略仍保留。
9. 真实缺失目标/验收不会被 UI 编造；相似开头但不同限制的段落完整保留。
10. 用户写的“重构范围”不因标题关键词被当成 AI 建议隐藏。
11. 相同业务 ID 的不同需求实例、不同工作区不会串线；迟到数据不覆盖当前实例。
12. 只读打开详情不产生模型调用、运行、证据写入或发布行为。

呈现与可用性：

- 同一详情视口只有一个强调的上下文主动作，关闭不重复；破坏性操作放入更多且维持确认。
- 默认首屏可识别标题、当前待办和主动作，正文不先被三个系统状态卡挤下去。正常短标题/短问题夹具在 1440×900、正常缩放下，首屏能看到目标正文起始；长文允许自然滚动。
- 重要阻塞不因页签化被隐藏，当前待办可带到准确问题，查看完整证据最多两次有意义导航。
- 需求正文和验收要求可读；TEST ID、路径、hash、规则码不常驻抢占首屏。
- 需求/交付/记录切换、回答后返回、反馈后返回都保留上下文。
- 1280/1440 桌面、窄容器、200% 缩放及手机宽度均无非必要横向滚动，footer 不遮正文。
- 深浅主题、键盘、焦点返回、页签语义、最上层 Escape 与 reduced motion 验证。

验证方法：

- 构造包含旧格式/缺失字段/组合冲突的真实数据夹具，运行对应逻辑测试与 UI 测试，不只断言按钮文案存在。
- 模拟当前截图状态，追踪每个按钮最终调用的真实 action、run 与版本；截图前后并排对比。
- 做小规模任务检查：打开后说出“这条需求做什么、现在为什么停、下一步点哪里”；记录完成时间、误判与查证路径。没有真实受试者时明确标为内部走查，不冒充用户研究。
- 不以卡片减少数量、DOM 减少、所有内容塞进一屏作为唯一成功指标。
- 执行适用项目测试与 contract 检查；旧测试若固化了错误交互，说明调整依据，不能为了绿灯保留冲突。

最终提供：根因与改动说明、信息去向表、共享动作状态矩阵、文件清单、真实插件截图/演示、交互与测试证据，以及未达标项目。不要以脱离插件的静态 HTML 代替实际交付。
