# 需求详情 v4：从目标到可验证交付

日期：2026-11-04。用途：可直接交给 DSH Harness / Codex 的重构执行指令。

后续专项补充：[需求描述 v5：意图到详情内容闭环](requirement-description-v5-intent-to-detail-brief.md)，明确澄清草稿、正式正文、来源确认与执行版本一致性；相关内容以该专项指令为准，其余 v4 约束继续适用。

本轮采用第一性原理的方法：质疑步骤的必要性 → 删除无效步骤 → 简化保留步骤 → 缩短反馈周期 → 自动化已经合理的流程。这是方法选择，不是对任何人物观点或认可的推断。

本文件覆盖 v3 的功能编排与页面信息优先级；[v3](requirement-detail-v3-direct-action-brief.md) 的完整页面、响应式、原地操作、无障碍和导航恢复规格继续适用。冲突时以 v4 为准。[已有原型](../design/requirement-detail-v3-layout-reference.html) 仅展示 v3 布局，没有实现本轮自动推进能力。

**这是一份待实施指令。当前仅检查源码和已有证据，没有操作真实需求、恢复执行器、签收或发布，也没有证明当前产品 E2E 已通过。**

## 1. 先重新定义这个页面的工作

用户打开需求详情，是为了理解目标、处理必要决定、检查交付结果。用户不应负责推动 REQ、CHG、RUN、CAND 等内部对象依次流转。

产品承诺：**人确认要得到的结果与可接受边界；AI 在授权范围内推进到可验证的交付候选；确实需要人判断时，带着事实和选项停下来。**

详情页面围绕三个问题组织：

1. 要解决什么问题，怎样算完成？
2. 实际做到了什么，证据和可操作结果在哪里？
3. 现在需要我决定什么；如果不需要，我可以直接离开吗？

优化目标是“更少的无效人工干预，更短的可信交付路径”。点击数、问题数和速度只在范围不变、验收标准不降低、权限不扩大、证据不失真的前提下比较。不能通过不提必要问题、隐藏失败或自动签收来改善指标。

## 2. 当前事实与本轮判断

以下依据当前工作区源码，而非把早期失败报告当作当前版本结论。实施前重新核对，记录源码版本与运行构建身份。

| 已检查的事实 | 能说明什么 | 本轮处理 |
| --- | --- | --- |
| `client.js` 仍有 `RequirementDetailShell`、`DrawerContent`、`Drawer`、页签和底栏；内层正文限宽 720px | v3 的独立详情页面尚未在当前源码落地 | 实施完整页面，不再在抽屉上追加新模块 |

| 已有决策路径与内容哈希、消费回执、同轮 `continue`、恢复上下文与并发复核 | 旧问题消费与同轮继续已有修复 | 保留这些约束，不把历史问题直接报告为当前复现 |
| `preflight.mjs` 不再强制 AI 二次评审，失败/过期验收可带入开发 | 部分不必要门禁已经移除 | 不恢复强制评审，不把可选建议当启动阻塞 |
| 原需求内自动修复最多两次，要求现存授权载体，保留暂停/取消/决策边界 | 已有受限修复能力 | 复用原需求原运行；不为每次失败新建需求，不偷偷创建新执行会话 |
| 候选绑定需求、工作区与验收证据；人工签收、发布授权独立 | 交付可信度依赖内容绑定和真实权限 | 保留；界面简化不能降低后端约束 |

本轮假设：不舒服的根因不仅是布局拥挤，还包括**把内部流程维护交给用户**。该判断需通过真实任务走查验证。当前没有新的宿主页面截图或专项复现，因此不能宣称 UI 导航异常、建议阻塞或澄清不收敛已在当前版本复现。

## 3. 先删除，再决定自动化

| 元素或步骤 | 决定 | 理由与替代行为 |
| --- | --- | --- |
| 同一状态的横幅、卡片、底栏重复说明 | 删除 | 一处当前事实，动作紧随事实 |
| “查看问题 → 打开另一层 → 回答” | 合并 | 原地呈现真实问题、影响、选项与提交 |
| 澄清完成后强制再做 AI 评审 | 保持删除 | 优化建议按需查看，不挡正常开发 |
| 无业务决定的“继续”“生成候选”“运行检查”常规接力 | 自动衔接 | 已授权且满足条件时由系统完成；异常时给明确恢复动作 |
| 为完整表单强制用户填写每个展示字段 | 删除 | 缺背景、负责人等展示字段不应天然阻塞；真实目标冲突、必需权限缺失才分类处理 |
| 把仓库可查证的实现选择问用户 | 移交 AI | 先查代码、既有约定与已回答内容，再在授权边界内实施 |
| 每次产品失败自动新建缺陷需求 | 保持不自动创建 | 原需求内记录失败、修复和复验；明确的新范围另走变更 |
| 永久展开日志、对象链、原始文件路径 | 默认收起 | 业务影响必须可见，诊断细节按需读取 |
| 全生命周期步骤条与推测进度百分比 | 默认删除 | 显示真实完成动作、当前动作与更新时间，不伪造确定性 |
| 真实业务取舍、越界授权、最终人工验收、发布授权 | 保留明确决定 | 属于用户责任，AI 不能代替 |
| 失败反馈、暂停/取消、查看证据与恢复能力 | 保留可发现入口 | 降低日常视觉权重，不删除控制能力 |

每新增一个按钮、状态或必填项，实施说明必须回答：它对应哪个用户决定？如果只是推进内部对象，为什么系统不能完成？不要只把按钮藏进“更多”，却保留底层死路。

## 4. 给 AI 清楚的边界，减少不必要提问

### 4.1 在启动前形成可读的交付约定

沿用已有需求事实，展示目标、本次范围、不包含事项、可观察验收要求。只有信息真实存在时才展示对应条款，不为了版式凑齐空模块。

原文足够清楚时可以直接开始；从已有明确事实提取结构不要求用户重复确认。AI 新增、推断或改变业务承诺时，先展示差异并由用户明确采纳；原始内容始终可追溯。结构缺失与业务歧义必须区分。合法格式问题优先无损修复，不能借“简化”绕过真实确定性门禁。

启动入口仍可叫“交给 AI 推进”。旁边用简短摘要说明本轮会修改当前授权工作区、验证结果并准备交付候选；不会自动签收或发布。沿用既有权限模型，不增加一个与现有按钮等价的强制确认弹窗。对既有运行，不追溯推定用户授权了新能力。

### 4.2 提问前必须经过的判断

按以下顺序检查，而不是一有不确定就打断用户：

1. 需求原文、验收要求、已确认回答是否已给出答案？有则复用，并保留来源。
2. 仓库和既有产品约定是否可查证？在合理预算内调查，不让用户代读代码。
3. 是否属于范围内、可逆、不会改变业务承诺的实现选择？是则 AI 自行处理并记录。
4. 不同选择是否实质改变范围、业务行为、数据处理、权限、费用或不可逆后果？是则带着事实请求决定。
5. 是否是环境/工具失败？先分类并尝试既有权限内的可行方式；不可恢复时报告具体阻塞，不包装成业务选择，也不扩大权限。

示例仅用于说明规则：组件复用、容器宽度、根据已有规范决定键盘焦点通常由 AI 处理。“返回列表是否保留筛选”若已有明确验收要求则直接执行；确实无约定且涉及新的业务承诺时，才提出一次清楚的问题。不能把示例硬编码为当前需求答案。

### 4.3 真正的决定必须一次说清

原地展示：要决定什么、为什么现有授权不足、必要事实、真实选项及影响、AI 建议、提交后的下一步。选项不预选，允许补充；建议不是授权。

多个独立且已知的问题尽量同轮呈现；有依赖的问题待前置答案后再处理，不为减少轮数制造伪选项。回答后不能换措辞重问同一问题；新事实确实使旧答案失效时，说明变化及其影响。

澄清预算与无进展规则作用于整个意图/需求会话，重启不清零。预算耗尽时输出已确定内容、剩余真实阻塞及恢复办法，不自动选择、不伪造确认。预算值在实施前读取既有规则；需要改变时记录原因，不另设一套互相冲突的上限。

## 5. 自动推进必须有确定性收口

不要为了本页新增通用工作流平台。优先在现有运行编排、证据与详情投影上补齐一条最小闭环。

```text
人确认目标与边界，启动本轮
  → 自动准备已有契约要求的执行条件
  → AI 实现与验证
      → 有效新决策：原地等待明确回答，再续原运行
      → 可修复产品失败：原需求内受限修复，再验证
      → 环境阻塞/预算耗尽/暂停取消：如实停下，给具体恢复方式
      → 满足现有候选条件：自动保存证据并准备交付候选
  → 展示可操作结果、验收条件与证据覆盖
  → 真人决定是否验收
  → 如需发布，独立授权与执行
```

模型 `idle` 只证明本轮对话停了。结算必须根据事实分流：

| 真实条件 | 系统动作 | 页面呈现 |
| --- | --- | --- |
| 新的未消费决策存在，或明确决策引用读取失败 | 停止自动继续；读取失败保留门禁 | 展示问题，或明确说明暂时无法读取并可重试 |
| 仍有授权内可执行工作、载体有效且预算允许 | 串行续原运行，不追加人类回答 | 当前动作与真实进展，无需人点“继续” |
| 满足既有候选条件、证据与内容一致 | 幂等生成/复用当前候选 | 交付摘要、结果入口、验收入口 |
| 产品失败且满足现有修复条件 | 进入原运行修复队列，最多两次 | “正在修复”与对应失败，不提前显示待验收 |
| 无授权载体、已暂停/取消/终止、范围越界 | 不自动恢复或创建新会话 | 明确原因；合法时提供需要用户操作的恢复入口 |
| 没有可证明的进展，或预算耗尽 | 停止循环，保留检查点与诊断 | 哪一步没完成、已尝试什么、可以怎么恢复 |
| 事件/数据不完整，无法确定 | 不猜测成功或要求无内容的决定 | “结果尚未核实”及重新读取/诊断入口 |

新自动衔接仅用于授权覆盖的运行。既有运行需要扩展授权时明确处理，不能因为页面换版就自动启动。保持已终止运行不可被迟到事件复活；宿主重启后的恢复沿用现有可信恢复规则，不能等同于现存载体自动续跑。

实施时定义并持久化自动衔接预算。没有既有配置时，可采用**每轮最多 3 次自动续推派发**作为初始保守值，独立于已有“最多两次产品修复”；在报告中列出实际采用的值、计数边界及理由。串行派发，重启不重置，人工回答本身不计为自动续推。每次续推前复核权限、当前决策、版本、运行状态与剩余预算。

“有进展”必须对应原验收条件的验证状态变化、可核实实现变化、真实阻塞消除或有效新证据。心跳、日志增长、重复总结、仅改时间戳不算。一次续推没有可证明进展即停止自动续推并解释，不能用计数尚未耗尽继续空转。错误可重试也必须有明确上限和幂等保障。

交付候选只证明“这是本次待验收的确定内容”。沿用现有生成门禁，展示各 AC 的通过、失败、待人工、未验证与证据；通用测试全绿不能冒充所有业务 AC 通过。需要人工体验的条目可以明确待人工，不能为了自动收口伪造通过。模型总结不能替代命令回执和行为证据。

## 6. 页面设计：让结果和决定成为主体

保持插件内容区内完整页面、单列阅读轴，无常驻右侧属性栏。宿主导航可见，返回恢复列表条件和位置。普通页面使用页面语义，不能保留抽屉的 `aria-modal` 或焦点陷阱。

```text
← 返回需求                                      反馈  更多

需求标题
真实目标的一句原文（有则展示）
低强调元数据

【根据真实情况只突出当前最重要的一件事】
需要决定 → 问题 + 影响 + 选项 + 原地提交
正在处理 → 已完成的具体动作 + 当前动作；可以离开
等待验收 → 改好了什么 + 打开结果 + 验收条件 + 验收入口
遇到阻塞 → 失败影响 + 已尝试办法 + 具体恢复动作
尚未开始 → 需求约定 + 交给 AI 推进

需求约定                              编辑/查看本轮约定
目标、本次范围、怎样算完成

结果与验证
结果入口、当前证据覆盖、已知限制

背景与原话 / 历史 / 技术详情                    按需展开
```

视觉记忆点是**当前问题或实际交付内容本身**，不用大状态卡片、仪表盘指标和装饰性流程图抢占视线。以下为实施约束：

- 需求标题 24–28px，正文 15–16px、行高约 1.6；正文最大 800px，页面单一左对齐阅读轴。窄屏按实际插件宽度降到 24/16px 内边距，沿用 v3 的详细尺寸。
- 沿用宿主字体与主题 token，系统中文字体清晰优先，不引入装饰字体、CDN、全新品牌色或大面积渐变。颜色辅助区分状态，文字与图标同时表达含义。
- 一处主操作随内容出现；暂停/取消为可发现的次操作，不将所有动作平铺成工具栏。原按钮离屏时才允许简短粘性操作条，不能覆盖正文或键盘焦点。
- 等待验收时优先“打开结果/预览”，再进入验收决定。只能在真实预览可用时显示；静态截图明确标注，不能伪装成交互页面。未部署就不写“已上线”。
- 保留完整验收内容与限制，首屏可以摘要并展开，但问题和选项不能被摘要截断。轮询不重排正在阅读的区域、不清空输入、不偷焦点。
- 执行中不显示假百分比。连接陈旧时说明最后更新时间及无法确认的事实，不仅凭心跳过期宣称执行器失败。
- 用户编辑需求时保留运行使用的版本。影响范围或验收的变更展示差异并走既有更新规则；立即标明旧候选/旧证据是否失效，不能将新正文与旧“已通过”拼成一个完成态。
- 可选优化建议位于按需入口，不占当前主任务、不强制生成、不默认采纳。合理业务术语、关键限制与业务链接不能因“技术内容过滤”被误删；保留可查看的原文与解析异常反馈。
- 空态只给有意义的动作，异常明确是数据、执行、证据或连接问题；不要求业务用户手工编辑 JSON、复制命令才能继续基本流程。

## 7. 后端契约与实施落点

先核对现有接口能力，复用已有模块；只有确有缺口才扩展契约。以下是行为约束，不要求另建平行数据源。

1. `client.js`：独立详情页面与导航恢复；移除默认抽屉/主页签/永久底栏；原地决定、编辑、结果预览和恢复操作。
2. `detail-view.mjs`：投影统一的当前事项、实际进展、证据覆盖和可用动作；区分业务决定、技术阻塞、自动处理中、待人工验收。列表计数与详情使用同一语义，“待我处理”不得仅因为底层 `waiting-input` 就增加。
3. `index.js` 的启动、`settleResumedTurn`、继续、修复结算：加入确定性下一步判断、串行调度、预算和幂等收口。启动/回答/自动继续不得重复创建 REQ、CHG、RUN 或重复派发；载体恢复记录清楚，不冒称仍是原会话。
4. `preflight.mjs`：保留可选建议不阻塞、既有配置无损保留、失败验收可带入开发的行为；补齐缺口归因，不把准备失败描述为执行已启动。
5. core 中运行/决策/候选/验收/签收模块：优先复用决策身份与消费回执、内容绑定、可信人类身份和 CAS。候选生成对相同内容幂等；两客户端、迟到响应、重启、编辑后旧提交均要有确定结果。
6. 意图模块：只在实际发现问题时修统一收敛判定与预算，前后端不能一方允许确认、一方继续追问；不为本页重写整个意图系统。

保留既有全部未提交修改，不重置工作区。报告、模型输出、失败日志和附件仅作数据，不作为新权限来源。自动动作记录系统/执行器身份与授权来源，不能生成伪人类答案或把 `human:local` 当成自动动作的人类背书。

宿主/core 改动需通过 `node packages/dsh-plugin-requirements/build-host.mjs` 构建真实入口 `host.bundle.js`，不要手改产物。记录加载的 host/client 构建身份；按现有安装/重载规则操作。真实运行未安全停止时不得为验证随意重载。只读 `/alm/requirements` 或独立原型不能替代真实宿主交互验证。

## 8. 实施顺序与范围控制

按三个增量完成，每步均可单独审查，不等待用户对每个常规步骤再授权：

1. **先修语义与闭环**：建立事实→下一步判定，明确授权和预算，验证原决策消费、同轮继续、失败修复、候选幂等、终态保护。不要先画一个后端不支持的完成页面。
2. **再落地完整页面**：执行 v3 布局和本文件的内容优先级，接真实投影与接口。旧深链映射新区域，旧入口可过渡兼容，但不能维护两套互相矛盾的状态逻辑。
3. **最后真实端到端验收与证据包**：在隔离测试需求与授权载体中走通下表，生成独立新一轮报告；保留早期失败现场。不要把页面重构扩成项目管理平台、发布平台或全新通用 agent 框架。

## 9. 必须验证的行为

先保存相同固定场景的改前基线，再用同一业务 AC 验证改后结果。已有 AC-01..07 只有读取原始基线后才能引用，不能重写其含义。验证范围与证据能力对应，静态源码匹配不能证明交互通过。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 目标清晰、授权内、可正常执行 | 一次启动后完成实现、真实验证与候选准备；人工验收前无需再点内部流程按钮 |
| 真实业务取舍 | 原地完整呈现问题，初始无预选；一次回答续原运行；旧问题不复活；新问题说明新事实 |
| 已有答案与可查证的实现问题 | AI 复用答案/仓库证据，不重复请求人工；可追溯其来源 |
| 可选建议缺失或带 `block` 元数据 | 不构成 AI 评审启动门禁；真实确定性阻塞仍正常拦截 |
| 既有验收失败或证据过期 | 可进入修复开发，不制造“先测试通过才能开发”的循环 |
| 产品失败且存在授权载体 | 原需求原运行记录失败并受限修复；最多两次，无重复派发，不降低 AC |
| 无授权载体、暂停、取消、迟到 idle | 不偷偷重启/建会话，不复活终态；显示具体原因和合法恢复入口 |
| 无进展、环境不可恢复、自动预算耗尽 | 有界停止，保留证据；不显示完成、不无限“继续”、不让用户回答空问题 |
| 并发点击、双客户端、超时重试、重启 | 不重复需求/变更/运行/候选/派发；状态与预算可恢复；冲突不冒报成功 |
| 决策内容变化或读取失败 | 旧回答被拒绝或要求重读，输入可恢复；不绕过待决策 |
| 需求/实现/验收变化 | 旧候选、证据及相关授权按绑定规则失效，页面和后端一致 |
| 待验收 | 可打开真实结果，逐项查看 AC 覆盖与限制；AI 不伪造真人签收，发布单独处理 |
| 返回、深链、刷新、未保存输入 | 需求可定位，列表条件和位置恢复，输入不静默丢失，无模态焦点陷阱 |
| 实际插件内容宽度 360/480/640/880/960/1280，缩放 200% | 不横向溢出、不遮挡主操作；长标题、长问题和多选项可完整读答；深浅主题与键盘操作可用 |

同时记录四组数据，不以单一数字宣布成功：

- **业务结果**：原 AC 逐项结果与可复核证据；未验证明确写出。
- **人工成本**：从意图开始到候选的人工轮数；区分目标确认、必要决定、内部流程点击和故障恢复。固定无歧义场景要求内部流程点击为 0；不要求所有场景零提问。
- **推进可靠性**：真实执行是否触发、重复派发数、重复问题数、自动续推/修复次数、终态误复活数；固定正常场景中重复派发、无新事实的重复问题、终态误复活均应为 0，自动续推和修复次数不得超过对应预算。
- **可理解性**：给未参与实现的真实使用者打开页面，检查能否在约 10 秒内说清目标、当前事实和下一步，并完成一次决定。自动化可查布局和流程，不能伪造人类体验结果；未做则记 `pending_human`。

## 10. 交付物与完成标准

交付真实实现、必要的契约说明、针对状态转换/幂等/权限/决策身份的有效测试，以及真实宿主端到端证据。纯边距改动无需增加镜像实现的测试。修改相关检查通过后，不无理由重复扩测。

在 `artifacts/requirements-detail-v4/<新时间戳>/` 输出：

- `index.html`：离线可读报告；改前/改后页面、问题与取舍、逐项场景结果、结果页面入口/截图、证据索引、已知限制。截图与用例标明真实/示例，报告内不泄露 token。
- `report.json`：场景、业务 AC、预期/实际、结果、证据路径、运行与构建身份、人工干预记录、自动预算使用、候选内容绑定、未验证项。
- `codex-handoff.md`：可复现步骤、事实与假设分开、问题严重度、源码落点、尚未满足的要求、下一轮建议；使 Codex 能继续定位问题。
- `manifest.json`：本轮证据文件的相对路径、大小与 SHA-256；清单自身不包含自身哈希。独立复核清单，不覆盖早期失败证据。

至少保留尚未开始、真实业务决定、执行中、自动修复、阻塞、待验收、已验收及内容变化导致证据失效的页面证据。截图只能证明当时外观，行为必须同时有操作记录、接口回执或状态变化证据。

分别给出 `technical_e2e`、`business_ac`、`ui_behavior`、`human_acceptance` 与 `release` 结论。单元测试全绿、模型调用成功、截图好看或候选生成均不能单独证明端到端成功。最终真实人类验收未发生就写 `pending_human`；未请求发布就写 `not_requested`，不为报告完整性自动签收或发布。

完成标准：用户不用学习内部对象流转；正常路径在已有授权内自动推进至可信候选；必要决定清楚且能原地完成；失败能够解释与恢复；任何完成状态均有对应事实。剩余不满足项应如实交接，不能以修改状态名称代替功能实现。
