# 需求详情页评估与优化建议

- 评估对象：`packages/dsh-plugin-requirements/client.js` 的需求详情抽屉（`Drawer` L2076 / `DrawerContent` L1730 起）与「查看详情」大弹窗（`DetailModal` L2112）
- 数据来源：真实宿主（54672）+ 浏览器 harness（63114 反代真实 API），三态实测截图与文本
  - `tmp/ui-shots-detail/unchecked-high.png`：REQ-ALM-001，未检查 / 风险 high / 缺口 acceptance-missing
  - `tmp/ui-shots-detail/blocked-dangling.png`：REQ-ALM-006，阻塞（悬空关系）
  - `tmp/ui-shots-detail/needs-clarification.png`：REQ-ALM-012（两条重复记录）
  - 同目录 `probe.json`：焦点、`aria-modal`、按钮 disabled 状态实测
- 角色视角：把「需求详情」当成研发/需求负责人每天要用的**决策页**来评，而不是展示页。

---

## 1. 结论（先给判断）

**可用，但首屏失焦。** 详情页目前把「承诺正文（含 AI 长报告）」「缺口（重复三遍）」「记录（关系/GitHub/历史）」混在一条长滚动里，用户打开后第一眼看到的是**一段被原样打印的 Markdown 和同一句话的两遍**，而不是「这条需求现在能不能动、缺什么、我该点哪里」。

三个最影响信任的问题：

1. **门禁可以被绕过**：`blocked`、`needs-clarification` 状态下底部「开始开发」仍可点（`probe.json` 实测 `disabled:false`），与页面上「尚未满足签收条件」的红字直接矛盾。
2. **下一步只是文字**：决策条右侧「下一步 · 登记验收命令」是不可点击的 `span`；用户看到指令但做不了，只能自己去猜入口。
3. **详情有两套**：抽屉（60vw 单列）与「查看详情」弹层（940px 双列）是两份不同的信息架构——抽屉把 AI 长文塞进「需求背景」，弹层才把评审/验收/版本分到右栏。用户点「查看详情」是合理的，因为它比默认抽屉更好用。

以及一个不该出现在产品里的缺陷：**打开抽屉后焦点没有进入抽屉**（`focusInsideDialog:false`，`aria-modal` 缺失，Tab 直接跑到抽屉外的列表按钮），键盘和读屏用户实际被困在背景页面。

---

## 2. 这个页面要回答的 5 个问题

| # | 用户问题 | 当前答案位置 | 能否一眼回答 |
| --- | --- | --- | --- |
| 1 | 这条需求现在能进入开发/发布吗？ | 顶部决策条 | 能，但「开始开发」仍可点，答案被自我否定 |
| 2 | 缺什么、怎么补？ | 决策条 + 质量与验收→证据缺口（重复） | 能看懂，但做不了（下一步不可点） |
| 3 | 它到底承诺了什么（范围/验收）？ | 需求背景（被 AI 报告淹没） | 难，需要滚动并过滤 AI 文本 |
| 4 | 谁在负责、什么时候改的、改了什么？ | 标题下 meta + 归属/历史 | 部分，无时间、无变更摘要 |
| 5 | 我能拿它去做什么（开工/评审/试演/归档）？ | 底部 6 个按钮 | 能，但主次不分、危险操作贴主操作 |

## 3. 保留的优点（不要推翻）

- **决策条置顶**且同时给「缺口 code」「修复提示」「签收条件」——方向正确，只是重复与措辞要收。
- **状态与证据分色**：未检查中性、阻塞红、需澄清/过期琥珀，文字与颜色同时表达，符合可访问性。
- **验收溯源**（`AcceptanceProvenance`）标出需求哈希/提交/环境/来源，未完成时明确「来源或版本不完整」——这是这个产品最值钱的差异点，应该更靠前、更显眼，而不是埋在验收小节底部。
- **关系与追溯**有独立入口（`查看追溯图`），GitHub 归属明确说「尚未建立」而不是造假。
- **主操作用反色按钮**，在深色主题下对比度稳定。

## 4. 问题清单（按严重度）

### P0 — 信任与可达性（必须修）

**P0-1 门禁与「开始开发」不一致（前后端都未拦）**
- 现象：`decision.state` 为 `blocked` / `needs-clarification` 时，底部「开始开发」`disabled=false`（probe 实测）；后端 `index.js` 的 `start` 分支（L616-624）直接 `openChange({requirementIds:[body.requirementId], …})`，**没有任何证据/决策状态校验**。
- 影响：用户可从 UI 或直接 POST 绕过证据门禁开工，整个「证据说真话」的产品承诺被这一个入口破坏。
- 建议：在 `start` 分支先按 `decideEvidence` 复算，非 `ready-for-human`/`verified`（按风险策略）返回 409 `evidence-incomplete` 并附 gaps；UI 的「开始开发」按同一判定 disabled 并展示缺口；如业务确实允许「带缺口开工」，必须是次要入口、要求理由并写审计，不能是主按钮。

**P0-2 抽屉打开后焦点未进入、未限制**
- 现象：`role="dialog"` 存在，但没有 `aria-modal`、没有初始焦点、没有 focus trap；`afterTab` 落到背景列表的「登记验收」按钮（`inside:false`）。
- 影响：键盘/读屏用户无法感知已进入详情，Tab 会逃到被遮住的页面。
- 建议：`aria-modal="true"`；`useEffect` 里聚焦容器/关闭按钮；Tab/Shift+Tab 循环限制在抽屉内；关闭后把焦点还给触发行（现有 `ModalShell` 已有焦点保存/恢复逻辑，可复用同一 hook）。

**P0-3 Markdown 原样泄漏**
- 现象：`renderBrief()`（L1577-1620）只识别 `#` 标题、`- ` 列表和普通段落；`**…**`、`> 引用`、`1. 有序列表`、行内 `` `code` `` 全部原样输出（截图中 `**[范围] 拆分为…**`、`> AI 结论（block）`、`1. **澄清与拆分**：…`）。
- 影响：这是用户看到的第一个内容块，直接暴露「系统没渲染好」，也让人误以为正文就是这些符号。
- 建议：补 bold/italic/blockquote/有序列表/行内 code/链接的渲染（内部已有 Markdown 渲染可直接复用则复用，没有就写 40 行安全渲染器，纯文本节点 + 白名单样式，禁止 `dangerouslySetInnerHTML` 或先转义）。

**P0-4 「下一步」不可执行**
- 现象：`下一步 · 登记验收命令` 是 `span`。
- 影响：页面让用户「去登记」，却不给入口。
- 建议：把它变成真实按钮，映射到已有动作：`acceptance-missing→打开验收登记`、`review-not-run→运行评审`、`fix-blockers→查看阻塞来源`、`fix-anomaly→定位冲突记录`、`stale→重新验收`。没有对应动作时不要渲染「下一步」。

### P1 — 信息架构与文案（决定好不好用）

**P1-1 缺口信息重复三处**
- 决策条（code + 修复提示 + 签收条件）、质量与验收→证据缺口（GapsList）、评审 block 发现（ReviewBlock）各说一遍。
- 建议：决策条只保留「状态 + 一句最关键缺口 + 主行动」；详细 gaps 收敛到「质量与验收」一处，按「阻塞项 / 待补证据 / 建议」分组，每条带可点击修复动作。

**P1-2 背景与目标重复、AI 评审混入背景**
- 来源数据：`requirements/briefs/REQ-ALM-001.md` 的「背景」与「目标」两节写入了同一段原话；已采纳的 AI 评审（长报告）也被追加进 brief，于是一起渲染在「需求背景」里。
- 建议（分两层）：
  - 展示层：`需求背景` 只渲染「原始诉求」；把 `## AI 评审建议` 之后的段落拆到独立、默认折叠的「AI 评审记录」区块，并标注「AI 生成 · 已采纳于 … · 可展开」。
  - 数据层（后续单独立项）：采纳评审时不要改写 brief 原文，把评审记录放 `.alm/reviews/<UID>.json` 并单独展示；这样原话永远可追溯。

**P1-3 「未检查」这个状态词与事实不符**
- 评审已采纳、验收未登记时，决策条仍显示「未检查」。用户会问：明明评审过了，为什么说没检查？
- 建议：状态词由「最关键的缺口」派生：`acceptance-missing→待验收`、`review-not-run→待评审`、`acceptance-not-run→待执行验收`、`needs-clarification→待澄清`、`blocked→受阻`；「未检查」只用于评审与验收都没跑。

**P1-4 中英混排与术语噪音**
- `风险 high`（应为「风险：高（P1 需 5 个视角）」并把原因写出来）、`AI 结论（block）`（应为「结论：需修改」）、`executor · 2026-10-31 23:57:31`（「报告生成于 2026-10-31 23:57」）、`.alm/acceptance/<REQ>.json，白名单 node / npm / pnpm`（技术路径只放「技术详情」）。
- 建议：界面文案全中文，技术细节只出现在折叠的「技术详情」；「风险」给 tooltip 解释规则来源。

**P1-5 历史空态误导**
- 未提交文件显示「没有 git 历史（工作区可能不是 git 仓库）」，但仓库是 git。
- 建议：区分「文件未提交（尚无版本历史）」与「当前目录不是 git 仓库」；后者才提示仓库问题。

**P1-6 两套详情并存、按钮语义重复**
- 抽屉与 `DetailModal` 布局不同；抽屉底部还有「查看详情」打开弹层，弹层里又是同一份内容。
- 建议：收敛为一个详情面（推荐把抽屉升级成弹层的双列布局：左「决策 + 缺口 + 承诺」，右「元信息 + 评审 + 验收 + 版本」），删除「查看详情」按钮；或反之只保留弹层，列表点击直接开弹层。

**P1-7 首屏缺关键元信息**
- 没有创建时间/最近修订时间、没有修订摘要、没有验收覆盖摘要（如「验收 0/2 已执行」）、没有风险原因。
- 建议：标题下加一行低强调 meta：`负责人 · 优先级 · 项目 · 更新于 2026-10-31 · 修订 v1`；决策条内加一行「覆盖：评审 5/5 · 验收 0/1」。

**P1-8 底部动作无分组**
- 6 个按钮平铺，「关闭归档」破坏性与主操作相邻；「查看详情」重复。
- 建议：左侧主操作「开始开发」（受门禁约束）+「运行检查」；中间「AI 评审 / 变更试演 / 运行验收」；右侧「更多（归档、复制提示词、在仓库中打开）」+「关闭」。归档二次确认框已有，保留。

### P2 — 打磨

- P2-1 正文行宽：抽屉 60vw 在 1440 下正文约 700px，可读但长文偏宽；建议正文 `max-width: 720px`，AI 长文折叠。
- P2-2 路径/ID 可复制：`REQ-ALM-001`、`requirements/briefs/….md`、`.alm/acceptance/….json` 加点击复制（已有 `CopyPrompt`，可复用）。
- P2-3 关系「暂无关系」应带「登记关系」入口，而不是死文本。
- P2-4 「验收」小节里 `没有 verified_by，COV-001 会失败` 直接暴露规则码；应写「尚未关联验收用例（会阻断验收）」并把 `COV-001` 放技术详情。
- P2-5 抽屉内滚动条与贴底 footer 在小窗口（<760px）会遮挡内容，建议移动端改为全屏页 + 底部安全区内边距。
- P2-6 加载态：切换需求时抽屉内容直接替换，无骨架/无过渡；建议 120ms 淡入或保持标题 placeholder。
- P2-7 `prefers-reduced-motion`：抽屉滑入/遮罩模糊未处理（当前无动画，主要是 `backdropFilter` 成本），低配机可关闭模糊。

## 5. 建议的目标信息架构（一屏内回答「能不能动」）

```text
┌ 顶部：状态 pill · 需求 ID(可复制) · 修订 · 关闭 × ────────────────┐
│ H1 标题（最长 2 行）                                             │
│ meta：负责人 · 优先级 · 项目 · 最近更新 · 来源                    │
├ 决策条（唯一，不重复）───────────────────────────────────────────┤
│ [状态] 最关键缺口一句 + 覆盖摘要（评审 5/5 · 验收 0/1）            │
│ 主行动：[登记验收命令] 次行动：[运行评审]                         │
├ 质量与验收 ─────────────────────────────────────────────────────┤
│ 缺口清单（分组 + 每条可修复）                                     │
│ 验收：关联用例 / 命令 / 最近证据（当前/历史 + 不完整提示）          │
├ 承诺与背景 ─────────────────────────────────────────────────────┤
│ 原始诉求（背景/目标 分字段，去重；正文 max 720px）                 │
│ ▸ AI 评审记录（折叠，标注生成时间与是否已采纳）                    │
├ 归属、关系与历史 ───────────────────────────────────────────────┤
│ 关系（可跳转/登记）· GitHub · 版本时间线（当前修订高亮，可对比）    │
├ ▸ 技术详情（折叠）───────────────────────────────────────────────┤
└ 底部：开始开发（受门禁）｜运行检查｜AI 评审｜变更试演｜更多 ｜关闭 ┘
```

## 6. 可测的验收标准（建议纳入下一轮）

1. `blocked` / `needs-clarification` / `acceptance-missing` 记录上「开始开发」不可用，且给出具体原因；通过键盘也无法触发。
2. 打开抽屉后：`aria-modal="true"`、焦点在抽屉内、Tab 循环不逃逸、Escape 关闭后焦点回到原行。
3. 详情中不再出现未渲染 Markdown 标记（`**`、`>`、`1.`、反引号），用含这些标记的 brief 断言。
4. 「下一步」按钮可点击并打开对应真实动作（验收登记/评审/定位异常），无对应动作时不渲染。
5. 同一条记录在页面上只出现一次缺口说明（决策条一句 + 质量区清单），无重复段落。
6. 未提交文件显示「尚未提交，暂无版本历史」，仓库非 git 时才显示「不是 git 仓库」。
7. 状态词与缺口一致（评审已采纳 + 验收未登记 ⇒ 「待验收」而非「未检查」）。
8. `风险` 显示中文并给出原因；不再出现 `executor`、`block`、`high` 等原文术语。
9. 1440×900 下首屏可见：标题 + 决策条 + 缺口清单第一条 + 主行动按钮（不需要滚动）。
10. 客户端刷新后以上在真实宿主（54672）中同样成立，截图留档。

## 8. 未验证与限制

- 未在 GUI 宿主窗口内直接操作（宿主需 token；本轮用同源 harness + 真实 API 验收），GUI 内的滚动穿透、`backdrop-filter` 性能未实测。
- 三态夹具为 `D:/DSH` 与 `tmp/list-fixture` 隔离数据；未在实际业务仓库验证超长 brief / 附件 / GitHub 关联态。
- 焦点缺陷用 Playwright `activeElement` 实测，未覆盖读屏软件（NVDA/VoiceOver）实际播报。
- 未评估浅色主题下的详情页（harness 仅有深色）。
- 数据层建议（brief 拆分评审）涉及 `alm-core` 与历史数据迁移，本文只给方向，不含迁移脚本。
